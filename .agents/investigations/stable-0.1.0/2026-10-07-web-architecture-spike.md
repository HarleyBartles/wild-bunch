# Web architecture research and audit criteria

**Status:** Primary-source web research on 2026-10-07, preceding the web source audit. This records assessment criteria and proposed direction, not adoption of a new framework, approved remediation or runtime proof. The installed app uses React 18, styled-components 6, TanStack Query 5, TanStack Router and Phaser; newer React documentation must not become a requirement to use APIs unavailable in React 18.

## Composition and display ownership

The user's chosen direction is vertical slices: a capability and its display, interaction state, hooks, API operations and tests stay together. Truly shared infrastructure and state have explicit owners. Components own their display contracts. A parent arranges its children and supplies supported inputs; it does not depend on their internal DOM structure or style their descendants through selector reach-through.

React supports composition through children and other JSX props. Prefer that over wrapper components forwarding a large unrelated controller. Props remain a useful explicit boundary; context is appropriate for genuinely shared dependencies/state, not an automatic replacement for every prop. See [React composition](https://react.dev/learn/passing-props-to-a-component) and [context alternatives and scope](https://react.dev/learn/passing-data-deeply-with-context). This ownership policy is our inference and the user's preference, not a claim that React forbids prop forwarding.

Keep styled definitions at module scope alongside their display owner, using semantic elements, explicit variants and transient styling props such as `$selected`. Use tokens for shared visual values. A shared button can own its appearances and supported size/intent contracts; a parent must not select its internal spans to reshape it. Owned markup inside one component can use local descendant selectors, but selectors crossing an independently owned component boundary need redesign. styled-components supports component selectors and className forwarding; those mechanisms do not by themselves establish a good ownership boundary. See [styled-components basics](https://styled-components.com/docs/basics) and [transient props and composition API](https://styled-components.com/docs/api).

Global reset, fonts, tokens and deliberately selected base defaults remain reasonable. Global feature classes and broad element rules that dictate every surface's layout conflict with the selected ownership model. Do not replace current code with a generic design-system inventory or ban generated styled-components classes. Shared primitives need present consumers and a real stable contract.

Custom hooks share stateful logic, not automatically a shared state instance. Extract repeated lifecycle/subscription/cache orchestration with a focused name and inputs; keep simple calculations as functions and local toggles local. Derive render values directly instead of mirroring server data through effects. Effects synchronize external systems, including Phaser and browser storage, with appropriate cleanup. See [custom-hook semantics](https://react.dev/learn/reusing-logic-with-custom-hooks) and [effect guidance](https://react.dev/learn/you-might-not-need-an-effect). Memoization requires a concrete reason rather than appearing on every callback.

## Folder layout

React does not prescribe one directory taxonomy. Feature-Sliced Design offers a useful ownership/import model: application composition above route/capability slices, with genuinely shared infrastructure below. It explicitly allows omitting layers and retaining single-use logic in its page. See [official layer guidance](https://feature-sliced.design/docs/reference/layers). We will evaluate dependency direction and discoverability, not demand all six layers or manufacture frontend entities for backend-owned game truth.

A candidate shape is `app/` for entry/providers/router/shell/global foundations, cohesive slices for start, town places, travel and player overlays, `shared/` for HTTP/query infrastructure and proven UI primitives, and a separately composed developer capability. Names and exact nesting remain a decision after source tracing. Grouping by `components`, `hooks`, `state`, `ui` and `utils` alone scatters one behavior; merely moving those same technical buckets beneath a giant game slice would preserve the problem. Tests and slice-specific assets can live with their owners; shared test infrastructure has a separate home. Public entry points should express useful boundaries without creating barrel cycles or re-exporting everything.

The user clarified one world-map capability per playthrough. Setup and travel are consumers with different selection rules, not owners of separate maps. Share the canonical map query and renderer through that capability's supported interface; keep starting-town and travel-confirmation state with the interactions that own it. Sharing here follows an actual game concept and existing reuse, rather than putting every multi-consumer component into a generic shared folder.

## TanStack Query and server authority

TanStack Query should own API-derived state. Query keys identify the complete resource, including session/town and any meaningful request parameters; colocated options/key factories can prevent drift between readers and invalidators. A UI context can supply the selected session identity and UI concerns without copying server resources into parallel local state. See [query-key contracts](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).

Commands can apply authoritative response data immutably and invalidate dependent read models. Await required invalidations when mutation completion must include refreshed data. Distinguish an HTTP failure from a legal game action result that reports failure but still changes time/resources. A successful response is not necessarily a successful player outcome. See [mutation response updates](https://tanstack.com/query/latest/docs/framework/react/guides/updates-from-mutation-responses) and [mutation invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/invalidations-from-mutations).

Loading, background refresh, error, missing resource and empty data are distinct states. Select retry/freshness policy deliberately for this game. TanStack's defaults include stale cached data and background refetch; the user's accepted stale-other-tab behavior requires no new realtime system. Consume query AbortSignals where cancellation matters, and guard responses/invalidation against session replacement. See [defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults) and [cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation). Independent read models need server version/coherence policy where inconsistent combinations affect actions; Query cannot manufacture transactional consistency.

## Audit lenses

Inspect source ownership, real callers, display contracts, parent reach-through, prop forwarding, repeated stateful orchestration, shadow server state, key/invalidation drift, stale response races, command pending/error behavior, phase/URL reconciliation, overlay focus and dismissal, browser/Phaser lifetime, responsive layout and player/dev separation. Trace suspect cases into backend contracts and actual consumers. Record confirmed contradictions separately from conditional race risks, unfinished features and design preferences. Do not infer browser behavior solely from source, require speculative feature completion or add one regression per finding.
