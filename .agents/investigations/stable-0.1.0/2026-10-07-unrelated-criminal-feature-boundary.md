# PG-009: Unrelated-criminal feature boundary

**Status:** Historical source-traced assessment linked from the [authoritative feature matrix](../../../docs/features.md). It records the pre-retirement implementation and decision boundary. PG-009-R has since removed the live unrelated-criminal code and tests and selected explicit pre-alpha playthrough invalidation; source references below describe that earlier tree. The separate [retirement outcome](2026-10-07-unrelated-criminal-removal.md) and [future addition](2026-10-07-unrelated-criminal-addition.md) record current disposition and deferred design.

## Separate removal and future-addition records

The user requested two independently tracked jobs. [PG-009-R](2026-10-07-unrelated-criminal-removal.md) owns the removal story, code scope and retained/history boundaries. [PG-009-A](2026-10-07-unrelated-criminal-addition.md) owns the deferred future story and integration obligations. This assessment retains source evidence and cross-feature impact; it is not a second independently maintained specification for those jobs.

The future story must explicitly say non-gang or unrelated. Gang members already have bounties, so saloon encounters may produce criminals who have bounties does not distinguish this feature. Case membership, warrant/legal terms, murder guilt and encounter role are separate concepts; do not expose hidden membership/guilt merely to simplify the UI or add non-gang people to the gang suspect roster. No independent aggregate or generalized NPC platform is implied.

## What exists today

[GameSession.LookAroundSaloon](../../../src/WildBunch.Domain/Game/GameSession.cs) passes CaseFile.Suspects plus citizen selectors into [BountyLoop.LookAroundSaloon](../../../src/WildBunch.Domain/Game/BountyLoop.cs). The ordinary deterministic pool contains eligible suspects, citizen roles and one nobody slot. The culprit is gated by release; unrelated warrants are not encounter candidates. Developer overrides support Suspect, Citizen and None. Thus the saloon selection half of the removal story is already the implemented shape, subject to the previously recorded gang confrontation/release defects.

[SeedCaseBuilder.CreatePublicWarrants](../../../src/WildBunch.GameContent/NewGame/SeedCaseBuilder.cs) creates seven gang warrants and adds the unrelated roster's 21 warrants from [CaseCharacterRoster](../../../src/WildBunch.GameContent/NewGame/CaseCharacterRoster.cs). [WantedPosterResolver](../../../src/WildBunch.Domain/Cases/WantedPosterResolver.cs) selects undiscovered public warrants, gates the culprit and excludes retired/taken-in IDs supplied through InvestigationLoop. Unrelated targets can therefore appear on posters without a corresponding saloon encounter path.

[UnrelatedCriminalLedger](../../../src/WildBunch.Domain/Cases/UnrelatedCriminalLedger.cs) owns active/taken-in/collected/retired warrant IDs, a replacement cursor and gang-count parity. Gang turn-ins reduce that parity and retire excess unrelated targets; unrelated turn-ins can activate replacements. This population-balancing rule is an existing implementation policy, not an inevitable requirement of the future user story. Poster selection filters retired IDs but does not restrict all unrelated warrants to the ledger's active set, so the current active-pool concept is not a complete encounter/discovery contract.

GameSession.SettleUnrelatedCriminalTurnIn accepts a WarrantId and isAlive, enters SheriffOffice, validates a known active unrelated warrant and disposition, then emits [UnrelatedCriminalTurnInSettled](../../../src/WildBunch.Domain/Events/UnrelatedCriminalTurnInSettled.cs). It requires no recorded encounter/capture. A source search found no production caller, only the method definition and explanatory comment. [TurnInToSheriffHandler](../../../src/WildBunch.Application/Games/Commands/TurnInToSheriffHandler.cs) calls the gang SuspectId settlement path instead. [SheriffPlace](../../../src/WildBunch.Web/src/flow/places/SheriffPlace.tsx) currently reads posters and records; it has no independent unrelated-criminal turn-in control. The saloon's armed/correct declaration branch orchestrates the existing gang sheriff settlement.

The [Domain investigation DN-03](2026-10-07-domain-layer-investigation.md) records incomplete ledger replay. [GameSessionEventReplay](../../../src/WildBunch.Domain/Game/GameSessionEventReplay.cs) rebuilds the ledger after replay from the final case/gang settlements, losing unrelated-specific history applied against the initial empty ledger. Snapshot persistence does not establish a complete event-authoritative feature. Neither story should claim that keeping current code already delivers the future loop.

## Tests and compatibility decisions

For removal, prove that a newly generated case supplies only retained gang/culprit warrants and no independent bounty target; use real content/model identity rather than an assertion about missing class names. Retained saloon tests must cover eligible gang members, citizens and nobody, preserve wrong declarations and hidden culprit gates, and reach confrontation legally without direct presence seeding. Gang turn-in must still pay once and reconstruct its wallet/settlement facts. Source-spent/return-visit poster behavior must still work with the smaller pool. Strengthen existing owners instead of creating a deletion-detector suite.

Feature-only tests include UnrelatedCriminalLedger unit/wiring/persistence cases and the ledger portion of full-replay fixtures. Shared wanted-poster tests currently use unrelated first-result expectations, roster entropy tests select unrelated warrants, and migration/component-completeness tests expect the ledger component. Classify each against live retirement versus retained compatibility; do not simply replace expected values until tests pass. The [Domain](2026-10-07-domain-test-followup.md), [Persistence](2026-10-07-persistence-test-followup.md) and [Web](2026-10-07-web-test-followup.md) follow-ups retain the detailed test-quality findings.

Removing unrelated entries changes poster selection's eligible pool and therefore results for the same seed/town/visit inputs. New versions may deliberately change newly generated content, but old setup/event history must not silently generate different authoritative facts through current content. Decide whether existing affected pre-alpha playthroughs are supported through a versioned legacy policy, migrated with preserved history, or explicitly invalidated. The migration strategy remains required in all cases; deleting applied migrations or dropping the database is not the default.

The future feature requires unknown/inactive target rejection, no capture without legal presence, alive-only dead-body rejection, duplicate settlement rejection, correct person/warrant matching even for equal display names, no false murder-case advancement, deterministic availability and replay after real settlement. Replacements and gang-parity tuning need explicit decisions before becoming tests. Their absence from 0.1.0 is not an obligation to build them during cleanup.

## Decisions still open

Confirm the detailed removal story's new-hunt poster scope and any display of supported historical unrelated warrants. Choose the historical compatibility/invalidation policy before planning deletion of event/codec/projection support. Account for changed poster availability and difficulty effects without manufacturing filler warrants. Preserve gang bounty functionality and citizen mistakes. Future unrelated gameplay remains deferred, and whether capture/turn-in is immediate within confrontation or a separately playable sheriff visit is a future product decision.
