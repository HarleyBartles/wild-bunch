# Working feature inventory for stable 0.1.0

**Status:** Active discovery record for the [stable 0.1.0 investigation](2026-10-06-stable-0.1.0-investigation.md). The user requested this inventory before further feature triage. It records claims, evidence, questions and dependencies as we discover them. It is not yet the authoritative shipped-feature matrix, a complete product inventory or proof that a capability works. No feature has been repaired or removed by this record.

## What counts as a feature

A feature is a recognizable player capability with an observable outcome and a coherent lifecycle. Consulting useful information can be a feature as well as performing an action. Travel between towns includes selection, preparation, progression, interruption and arrival; an endpoint, component, event type or folder is an implementation part rather than automatically a separate feature. Split a broad capability when its parts have independently meaningful outcomes, availability or release decisions. Keep stable IDs as the grouping evolves and record splits/merges so findings remain traceable.

Distinguish player features, developer capabilities and supporting platform requirements. Inventory, time, heat, difficulty and entropy may be mechanics used by several features; displaying a value is not proof that the advertised gameplay system exists. A named action, visible control, source comment, ADR or test title is evidence of a claim, not evidence of successful delivery. Historical event/schema support is a compatibility obligation, not current player functionality.

## Discovery and assessment rule

During subsequent investigation and brainstorming, add each newly discovered feature-shaped claim here or attach it to an existing row. Record the evidence and unresolved boundary immediately; do not wait for implementation or silently treat a class name as shipped scope. When discussing a disposition, check both consumers and dependencies. Update an existing claim when new evidence changes its assessment rather than creating duplicate features for different screens.

Each assessed feature needs: stable ID and name; audience/player promise; entry point and availability prerequisites; supported outcomes, failure/recovery and resume behavior; authoritative state/events/read contracts; cross-feature dependencies; actual test evidence and its limits; current implementation assessment; and agreed release disposition. The table below is a first grouping with incomplete fields, not permission to fill unknowns with plausible behavior.

Assess implementation as coherent, broken, partial, unreachable or planned only where evidence supports it. Record not assessed where the path has not been traced. Mark source assessment separately from runtime/browser evidence. Keep release disposition separate from implementation status: a broken feature may be retained and corrected, while a partial one may be removed and deferred.

Dependencies need direction and meaning: requires, conditionally requires, consumes output, or changes another capability's state. Do not infer a hard dependency from incidental imports, shared folders or typical player sequencing. Name the precondition/data contract and its effect on availability. Shared event authority, command legality, CQRS and persistence are cross-cutting obligations; they are not a reason to draw a dependency from every feature to every other one.

**PG-006 named challenge and confrontation:** The [saloon challenge contract](2026-10-07-saloon-challenge-contract.md) records observation by distinguishing feature, optional challenge requiring a named identity, and a take-in attempt that can meet resistance, escape and health loss. **PG-006 citizen take-in nuance:** Citizens always come quietly, are released by the sheriff, and incur a small wasting-time fine for the player. They do not enter suspect resistance rolls, generate bounty or advance gang roundup. This settles the live citizen outcome; future killing of an innocent remains murder/arrest. Exact fine amount and insufficient-cash handling remain design details in the [saloon contract](2026-10-07-saloon-challenge-contract.md).

**PG-006 equipment split:** A gun is required to compel a wanted-person take-in; ammunition is not. With no gun the person refuses, rather than automatically fleeing. Citizens cooperate regardless. Future gunfight challenges remain available with no gun or no ammunition and result in player death; gun plus compatible ammunition is necessary to win, not a submission prerequisite. Separate ownership and combat capability in the [saloon contract](2026-10-07-saloon-challenge-contract.md) and tests.

**PG-006 correct declaration versus future recognition:** For the current release, the player must correctly name the wanted person; another wanted gang member brought under the wrong name does not qualify for bounty/roundup credit. Future sheriff recognition depends on that person's poster having circulated to the receiving town's sheriff office. Record circulation and town-specific sheriff knowledge as a deferred capability, separate from player-known posters and globally generated warrants. See the [saloon contract](2026-10-07-saloon-challenge-contract.md).

**PG-006 wrong-name live settlement settled:** The user approved release, a small fine, no bounty and no gang-roundup credit when a person is brought in under the wrong name. This applies to misnamed wanted gang members as well as the previously settled citizen outcome; citizen cooperation versus wanted-person resistance remains distinct. Future local sheriff recognition is deferred.

## Eventual authoritative feature matrix

The user wants a durable authoritative feature matrix, including cross-feature dependencies. This working inventory will feed that artifact after feature boundaries, claims and dispositions are reconciled. Choose its durable product-document home and owner in the specification; a product matrix is legitimate repository documentation rather than an agent workflow or implementation plan. Do not create two independently maintained matrices.

The durable matrix must distinguish current supported behavior, known incomplete/disabled scope and explicitly planned capabilities; link evidence/owning contracts and record directed dependencies with their meaning and conditional prerequisites. Lifecycle guidance must route feature changes and reviews to read/update it. Changes to a capability, dependency or release promise must update the matrix, related tests/contracts and material ADR history as appropriate. Implementation plans link to this authority; they do not redefine the feature promise.

Before publishing it as authority, reconcile every candidate and new claim against real entry points, command/read/replay paths and meaningful test evidence, and settle unresolved product decisions with the user. Promotion is an authored consolidation, not a copied inventory stamped complete.
