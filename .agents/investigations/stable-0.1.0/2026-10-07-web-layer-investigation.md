# Web layer investigation

**Status:** Static investigation for the interactive stable `0.1.0` baseline, following the [web architecture spike](2026-10-07-web-architecture-spike.md). Findings are proposed dispositions, not approved remediation. No application code, tests, browser session, service or persisted history was changed or exercised.

**Scope:** All 89 tracked application, configuration and guidance files under `src/WildBunch.Web`, excluding test files/directories and the generated lockfile, were read across the investigation. The lockfile's resolved principal runtime versions were inspected: React 18.3.1, styled-components 6.4.2, TanStack Query 5.100.14, Router 1.170.16 and Phaser 3.90.0. The tree has 136 tracked files in total: 89 in this source assessment, one generated lockfile and 46 test/support files. Relevant tests were selectively reassessed against findings; this does not claim a fresh full read of all 46 test/support files. The earlier [test-quality investigation](2026-10-06-test-quality-investigation.md) remains applicable. Supporting backend contracts and handlers were traced where needed.

**Dated disposition, 2026-10-08:** The manual town-layout override panel and its prep/set backend were retired from the 0.1.0 candidate. Findings and inventory rows about that panel remain historical evidence, not current implementation recommendations; see the dated [Web test follow-up](2026-10-07-web-test-followup.md) and [developer control feature record](../../../docs/features.md#dev-001-developer-salt-controls). Ordinary generated layout display remains part of the game map contract.

## Architecture direction and folder ownership

The user selected vertical slices with component-owned display contracts. Keep start/setup, town/store/sheriff/saloon, travel and player reference surfaces cohesive with their current hooks, API operations, state and tests. Application composition owns providers, routing, shell and global foundations; genuinely shared infrastructure/primitives sit below capability slices. Developer tools are separately composed for playtest. Shared context is appropriate for selected playthrough identity and genuinely shared UI state; TanStack Query owns server resources. Do not copy domain authority into a frontend state machine.

The current structure is mostly technical buckets. Store spans `flow/places`, `components`, `state` and `hooks`; travel spans those plus `components/start-flow/PhaserMapHost`; setup spans `flow`, `components/start-flow`, `hooks`, `ui` and `api`. A flat components directory includes whole play surfaces, obsolete cockpit fragments, shared primitives and feature-specific forms. The `dev` subtree already groups its API/types/panels/overlay more coherently, though it still imports start-flow internals and the universal session controller.

A candidate destination is `app/`, cohesive route/capability slices and `shared/`, with independently composed `dev/`. Exact names and slice granularity remain open. Town places can be grouped under a town capability without sharing a universal place controller; travel preparation and progression are related parts of travel. The map has two current consumers and deserves a supported shared map contract or explicit cross-slice API; the segmented toggle has player and dev consumers and belongs with proven UI primitives. Keep a backend-wide transport DTO genuinely shared when multiple capabilities consume it, while splitting the mixed API inventory by purpose. Do not mechanically create every FSD layer, move everything under one giant game slice, add frontend entities mirroring every C# aggregate or freeze folder names in tests.

Props are not themselves slop. InventoryPanel's inventory input and JourneyDecision's encounter/resources/intents are understandable display boundaries. TravelActions actually uses its session and pending flags; its forwarding does not justify a new context by itself. FieldReportPanel's large pass-through contract is obsolete scaffolding with no mounted source consumer. The larger ownership problem is GameSessionProvider exposing the entire controller, every unrelated action, raw setters and globally fetched store offers to every consumer. Its value memoization depends on freshly constructed session/refresh values and is not evidence of render isolation. Narrow subscriptions and ownership before considering measured performance changes.

## Findings

Source paths in this section are relative to `src/WildBunch.Web/src` unless explicitly qualified. Confirmed contradictions are separated from conditional races, incomplete features and design choices.

### WB-01: Technical buckets and a universal context obscure capability ownership

`state/GameSessionProvider.tsx:8-92`, `hooks/useCurrentGameSession.ts` and the scattered imports described above combine session selection, posters, investigation, setup, travel, purchasing, feedback and cache writes. Store offers load globally even outside the store, whenever a town is present. The provider exposes raw `setSession`, `setNotice` and `setError` alongside all commands. This is coupling and poor discoverability, not proof of a measured performance defect. Move behavior to cohesive slices, retain shared identity/resource access, and compose intentional boundaries. Extract repeated cache/command orchestration where the responsibility repeats, not one wrapper hook per callback or a universal command configuration engine.

### WB-02: The same server resource has independent caches and a shadow state copy

`useGameSessionQueries.ts` loads a session under `['session', gameId]`; `useTravelPanelState.ts:62-73` loads the same endpoint under `['travel-session', gameId]`, seeded with initialData. The travel cache survives panel unmount and is not removed by reset/archive. General session/dev commands do not update/invalidate it, so remount/background refresh can temporarily display a different session from the shell. `useCurrentGameSession.ts:39-49` mirrors wantedPosters into state; the read mutation also sets that copy and selection effects then reconcile it. Use one session resource/key with focused selectors, derive posters from authoritative query data, and keep only selection intent local. Cache consistency must be proved across mounted surfaces, not just inside an isolated TravelPanel.

### WB-03: Invalidation omits developer readers and cross-resource dependencies

`useGameSessionMutations.ts:46-54` refreshes only session/actions/journal. Developer audit/saloon/travel/session queries stay cached after normal gameplay. Developer mutations refresh only their own context and do not refresh player session/actions/journal or other affected dev readers. This can leave an already-open saloon panel showing a consumed override or session panel showing stale time/difficulty. Focus/remount refetch may eventually repair the display; it is not command completion proof. Define affected-resource ownership and shared keys/options, await necessary refreshes, and keep session identity captured with each operation. Separate independently queried read models still need backend coherence where versions matter; the client cannot provide a transaction by issuing Promise.all.

### WB-04: Manual travel preview state can become stale and failures vanish

`flow/TravelPrepSurface.tsx:86-119` fetches outside Query, depends only on gameId/destination and does not clear the old preview when a new request begins. Resource/mode/current-town changes with the same destination do not refresh it. A response failure clears it without showing the error; previewLoading is written but never rendered. Selection state is not reset on session/town change. The confirmation derives its heading from the current destination while displaying whichever preview is present, and does not gate against preview freshness. The Back to town button inside confirmation only deselects, returning to the map. Own selection plus a keyed preview query inside travel, display actual loading/error/rejection states, and validate destination/preview identity before starting. Preserve the existing cancellation guard's useful stale-response protection; move it to the proper query lifetime rather than removing protection.

### WB-05: Edited seed text is never the submitted seed

`useStartGameSeed.ts:73-78` updates seedDraft and seedDirty, but no live code decodes/applies that draft to seedState. `PreSessionSurface.tsx:48-56` encodes seedState. SetupHuntStep accepts decodeError/seedDirty but cannot produce decoding errors; seedDirty is unused. Randomize works because it updates both values. A valid pasted seed or invalid edited text is silently ignored on Ride on. Validate the submitted draft at the owning start boundary and send its normalized value; reject invalid intent visibly. Remove the obsolete Apply-era draft contract if there is no separate apply action. The existing StartFlow assertion only checks seedCode truthiness, and SetupHuntStep's injected decode-error test does not establish live validation.

### WB-06: Resuming the prologue loses its authoritative generation inputs

`useStartGameSeed.ts:44-53` restores only player name. Difficulty/entropy always initialize to Standard/Classic, and seedState to canonical, regardless of an existing session. `PreSessionSurface` passes these local values into `StorySoFarStep`, whose query regenerates the descriptor using them. The server's GetPrologueHandler derives the culprit descriptor from seed/difficulty/entropy. A refreshed random/custom setup can therefore display a story for different inputs from the saved hunt. Public GameSessionDto exposes difficulty/entropy but no seed, so merely hydrating two fields is insufficient. Supply a session-bound prologue/read contract or retained authoritative start metadata under an agreed API change; do not infer hidden truth or generate replacement seed state. Prove nondefault setup, refresh/resume and the same story/next phase.

### WB-07: Pending lifecycle commands and dual step state permit duplicate intent

`useCurrentGameSession.ts:93-111` omits setup, prologue, start-with-town and arrival acknowledgement from busyMode/loading. SetupHuntStep's submit is disabled only for blank name; StorySoFarStep checks only its GET; StartingTownStep keeps canvas interaction available. Repeated clicks can issue multiple lifecycle commands. PreSessionSurface simultaneously uses backend phases and local steps: deriveEffectiveStep prioritizes town-selection, so setting local creating does not show CreatingStep while the real backend remains in town-selection. Existing StartFlow mocks return GameStarted from getGame throughout, permitting local-step progression and concealing the actual pending phase. Use backend phase plus explicit pending/error UI state, prevent duplicate intent, and keep failed operations retryable. Async callbacks typed as void or invoked with void do not catch mutateAsync rejection; mutation onError displaying a message does not consume the rejected promise. Handle failures at the interaction boundary without inventing another canonical flow state.

### WB-08: Query errors collapse into absent game state or endless loading

`useGameSessionQueries.ts` exposes query objects internally, but useCurrentGameSession returns only loading and its separate command-error state. Failed session/actions/journal reads are not surfaced as distinct errors. Missing or unavailable stored sessions can look like a new game while the stale ID remains selected. StartingTownStep explicitly treats isError and empty map as pending; TravelMapSelection treats any missing data as unfolding indefinitely, including failure. The route Suspense fallback is an empty styled div, and there is no authored error boundary around chunk/render failures. Preserve background data where appropriate, distinguish missing/error/empty/loading, and supply meaningful recovery. Reconcile invalid stored identity with the server under the retained lifecycle contract rather than clearing a playthrough merely because a transient fetch failed.

### WB-09: Purchasing has no owned pending state and weak input semantics

`GameSessionProvider.tsx:43-75` calls buyStoreItem directly, without useMutation or pending state. StoreOffersPanel disables Buy using unrelated global loading and catalog loading, so the request itself leaves Buy enabled. The provider catches errors, meaning the row cannot distinguish completed purchase from failure via its promise. Quantity parsing silently turns blank/nonfinite input into one and truncates fractional input; number-input constraints are not applied through a submitted form. On failure it installs currentSession but skips dependent actions/journal/catalog refresh, which matters if the backend result changed facts. Move purchase into the store slice with an explicit pending/result contract, legal quantity handling and authoritative refresh for every changed result. Preserve backend validation and do not promise client disabling alone gives server idempotency.

### WB-10: HTTP success is confused with successful gameplay outcome

Travel, encounter-result forwarding and investigation callbacks put result.message into notice and clear error without checking success, while purchasing uses a different policy. A rejected action can appear in a success-colored notice; arrival acknowledgement errors are stored globally but TrailFlowSurface's completed branch renders no error/notice, leaving the player without visible failure feedback. Define gameplay result presentation separately from transport errors, while applying any lawful costs/state returned by an unsuccessful action. Do not suppress authoritative changes just because success is false or impose a blanket failed-action/no-event rule. Keep notices scoped to the relevant interaction instead of using one stale global command-error string as every overlay's read failure.

### WB-11: HTTP infrastructure loses status and masks invalid responses

`api/httpClient.ts:15-37` drops structured status/code/body into Error(message), then archive recovery searches message text for already archived or 409. Other conflicts could be misclassified if the numeric text appears, and structured ProblemDetails titles can hide useful details. JSON parse errors become null, which is cast to the caller's DTO even for successful responses. Header construction is overwritten by the subsequent `...init` when init.headers is supplied, so the advertised Content-Type merge does not work. Current API calls do not provide custom headers; that part is latent contract debt. Queries do not forward AbortSignals. Keep one typed transport failure/response policy, preserve relevant status and validation details, reject malformed required JSON, and support cancellation and headers deliberately. Empty-body commands must remain valid. Missing VITE_API_BASE_URL defaults to the player's localhost in a deployed build; the accepted same-origin deployment requires explicit configuration and deployment validation, not an unrequested host redesign.

### WB-12: Overlay lifetime and dismissal are not composed safely

CockpitOverlayFrame declares aria-modal but has no focus trap/background inert handling. Its effect depends on onClose; GlobalOverlays supplies fresh inline callbacks, so unrelated parent updates run cleanup/focus restoration and recapture/focus the Close button. ConfirmDialog repeats focus lifetime in an effect depending on onCancel and busy. Nested settings/confirmation dialogs both register global Escape listeners: Escape can close the settings frame even when the confirmation refuses dismissal while archiving. The dev drawer has another listener and can coexist with player dialogs. Use one compositional overlay/focus lifecycle with stable open/close ownership and topmost dismissal; distinguish the nonmodal dev workbench from modal player dialogs. Keep accessible naming without mandatory visible product headers. The [WAI modal pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) supports contained focus and inactive background. Browser keyboard/mobile proof is required after correction; static inspection is not that proof.

### WB-13: Styled components do not yet guarantee display ownership

`components/travel/travelShared.tsx` styles all spans beneath SectionHeader; TravelSummary's independently styled StatusPill uses two !important declarations to override that reach-through. Shared Field styles arbitrary descendant inputs/selects/spans, and PanelHead/StatusCard style supplied headings without an explicit child display API. These are weak shared contracts even though no plain className styling was found in production TSX. Replace cross-component selectors with owned elements, supported slots/variants or intentional typography inheritance. Selectors over one component's own markup, such as a local owned dt/dd block, remain legitimate. The global h1 size/font/margin rule is permitted by current doctrine but imposes a visual contract on every surface; reconcile that rule with the user's stronger preference before moving it. Tokens/reset/base semantics are not all slop.

### WB-14: The world map lacks keyboard-operable town selection in both interactions

PhaserMapHost renders a role=img container and pointer callbacks only. StartingTownStep and TravelPrepSurface provide no equivalent town controls, so keyboard users cannot choose a starting town or destination. TownHubSurface's visible building buttons are a useful existing pattern. Keep the canvas display and add a real supported selection path with the same eligibility and pending behavior. Do not remove useful accessible text just because an old test asserts that the previous destination list disappeared. Existing map tests call scene methods directly; they establish intent callbacks, not browser input accessibility.

The user clarified the ownership principle: one playthrough has one world map, used for different interactions. This is already one renderer, not two map implementations. Both API endpoints, starting-town-map and world-map, invoke GetStartingTownMapHandler with the same query and return the same projection, while the frontend maintains separate query keys. Consolidate the canonical map resource and its public component contract under a world-map capability; setup owns starting-town selection and travel owns destination selection, eligibility and confirmation. Do not make travel depend on setup internals or duplicate world-map data ownership merely because the interaction differs. Review endpoint/DTO naming and compatibility with this finding rather than deleting an alias without checking consumers.

### WB-15: Phaser hover replaces the configured building scale

`TownHubScene.ts:406-417` sets sprite display size from the layout, then pointerover sets absolute scale to 1.05 and pointerout to 1. Phaser's version-matched [Size source](https://raw.githubusercontent.com/phaserjs/phaser/v3.90.0/src/gameobjects/components/Size.js) establishes display dimensions through scale; [Transform source](https://raw.githubusercontent.com/phaserjs/phaser/v3.90.0/src/gameobjects/components/Transform.js) sets absolute scale. A source sprite whose intrinsic dimensions differ from the configured layout therefore changes size/aspect and fails to restore its fitted dimensions after hover. Preserve both baseline scales and multiply/restore them, or use an equivalent supported display contract. Rectangle fallback's initial scale is one, so do not misclassify that branch. Current scene doubles store displayWidth independently from scale and often discard event listeners; they cannot detect the real behavior. Strengthen the renderer contract and perform a real browser hover check when repaired.

### WB-16: Phaser lifetime and shared geometry need a clearer boundary

Both hosts correctly destroy their games during effect cleanup and keep latest callbacks through refs. That is valuable existing behavior. PhaserMapHost recreates the game for selectedTownId and selectableTownIds; TravelPrep recreates the latter array on each render, causing needless recreation on unrelated notices/query updates. TownHubHost also rebuilds on changed actions/layout, which may be a reasonable simple policy but should be explicit. Co-locate hosts/scenes, expose stable selection/update semantics where needed, and share the genuinely repeated grid/hash/asset-resolution rules inside the town-rendering capability. Do not create a generic Phaser framework solely to merge two short effects. Optional tile-grid fallbacks, fixed 10x10 geometry and inclusive coordinate edges need an agreed supported payload/version boundary before stronger validation; do not invent malformed input reachability.

### WB-17: The town-layout dev control is routed into the wrong lifecycle phase

DevPanelRegistry exposes town-layout only on town. useDevSurfaceSync derives town only after GameStarted. SetTownLayoutSaltsHandler explicitly accepts only GameStatus.Prepped. Thus the normal panel location cannot perform its advertised set operation. GenerateRandomTownLayoutSaltsHandler only produces a draft bundle and does not mutate the session; the panel's subsequent Set remains rejected. Relocate/redesign the control around lawful preparation if retained, or remove/defer it rather than silently allowing active-world rewriting. Its mocked API-call tests prove neither accepted phase nor visible world consequences. This extends the earlier Application lifecycle finding rather than prescribing new layout gameplay.

### WB-18: Town-layout data, draft and asynchronous lifetime are conflated

TownLayoutDevPanel manually fetches salts into the editable draft, with no cancellation or identity guard. A slow response for a previous game can overwrite the current game's form. It does not clear salts when gameId disappears, and writes do not refresh shared server readers. Clipboard writeText is not awaited but reports success immediately. Timers can clear newer status messages, are never cleaned up, and an initial fetch error is hidden by the No salts loaded branch because statusMessage renders only when salts exists. Keep query data separate from an intentional draft, reset draft by identity, handle async clipboard results, clean up status lifetime and make errors visible. A hook extraction should own this real repeated async responsibility, not conceal draft/server ownership.

### WB-19: Developer command orchestration is repeated and refresh is incomplete

SessionDevPanel, SaloonDevPanel and TravelDevPanel repeat local pending/error, try/catch/finally and refresh patterns instead of mutations with a shared affected-resource policy. Their refresh promises are not awaited. They ignore context-query errors and render fallback values as state, unlike SessionAuditDevPanel's explicit error display. Session difficulty/entropy toggles remain enabled while actionPending is true; concurrent commands can race and one finally can clear the flag while another is running. Form selections can survive a change of gameId. Retain truthful preparation and backend candidate selection, including Saloon's explicit hidden-truth frame and mismatch warning. Extract a focused mutation/refresh policy and supported shared form primitives; do not collapse all dev tools into a universal editor.

### WB-20: Case display invents ranking/provenance and uses names as identity

CaseFileSurface takes the first three visible clues when none is tagged CulpritTrail, then calls them the strongest known leads. No backend ranking establishes strength. findSuspectDiscoveryBasis treats any matching named record as wanted-poster discovery, otherwise substring-matches descriptions/names and source copy, with Player observation fallback. Captured warrant/poster filtering joins normalized display names, despite record/poster/suspect IDs being present. This is not proven hidden-culprit leakage, but it manufactures player-known provenance and can conflate distinct same-name identities. Render supplied facts honestly and request explicit player-safe links/provenance if the surface requires them. Split the large display into cohesive case-board sections without inventing a frontend case domain or extracting every calculation into a hook. Keep supported inference rules only when the owning model actually specifies them.

### WB-21: Travel diary invents successful resolution prose

TravelDiaryDayCard.tsx:86-98 renders every fight as forcing the rider off the trail and every positive ammoSpend as one round, although the domain accepts up to six bullets and failed fights explicitly keep pressure on. Run/bribe summaries similarly infer outcomes from choice ID. The server already supplies authoritative first-person messages in the diary/history paths; the DTO's resolution summary lacks enough facts to infer success. Render those messages or provide an explicit retained outcome contract. The current prose test uses ammoSpent=1 and only matches I stand and fight, so it misses both multi-round and failed outcomes. Do not solve this by translating more choice names into fictional results.

### WB-22: Public/playtest composition and player copy remain mixed

AppShell unconditionally imports/mounts DevOverlay and its registry/API tree, offers a Dev toggle, and runs dev surface synchronization. This contradicts the agreed direction that public deployment excludes developer controls; hiding a button alone would not enforce backend isolation. Establish environment composition with the backend boundary in the cloud slice. Player surfaces still explain implementation: TravelPanel says player-facing and backend; WantedPosterSurface talks about public-safe hints and portrait renderability; CaseFileSurface offers a dashboard-like deductions inventory; index.html is titled Wild Bunch Cockpit. Preserve useful game information and internal diagnostics in playtest, but remove development explanations and unsupported assurances from player display. This is audience/copy debt, not a request to redesign every surface into parchment.

### WB-23: Unmounted scaffolding and stale contracts survive the routed game

No non-test source consumer mounts AvailableActionsPanel, FieldReportPanel, TravelRoutesPanel, StartGameOptionsForm or SetupSeedSummary. SeedCodeEditor is reachable only through the unused options form. Notice-board and telegraph investigation handlers are exposed only through the unmounted AvailableActionsPanel; TownHub deliberately disables Telegraph, so some implemented actions currently have no normal player entry. Decide retained feature scope and either integrate the owning interaction or retire the old shell; do not preserve it as a hidden alternative UI. useStartFlow exports unused goBack/buildStartGameRequest; seed decoder imports/error helper are dead in the live hook; useGamePhase includes unused setup/JourneyStatus distinctions; DevOverlay userSelectedRef is written but never read; expanded props in several panels have no styling effect. Legacy API alias casts, optional old POI fields, unused formatters and duplicated numeric option maps require caller/compatibility review before retirement. No test is required merely to prove a dead export was deleted.

### WB-24: Style enforcement, responsive sizing and type contracts overstate guarantees

The existing styling detector bans selected legacy class names and certain source spellings, not arbitrary global class styling or selector reach-through. Its scanner behavior tests can remain useful if that validator remains a supported tool, but old filename/class-removal expectations are migration detectors. Routing convention tests freeze flat/lazy source syntax and find any return {}; they cannot prove the actual route parser or rendering. Replace obsolete detectors under the earlier test dispositions and enforce selected style through real tooling/review; package.json still has no lint/format commands, matching F-009. TravelHeader and TravelSummary's two-column layout lack narrow-width adaptation; dialog fixed padding/overflow and drawer height minus a wrapped chrome bar need browser proof, not a declaration of observed mobile clipping. TownLayoutDevPanel references undefined bg-soft/bg-strong tokens. API types omit GameStatus.Prepped and type nullable backend CurrentTownId as string; broad casts treat unvalidated payloads as complete DTOs. These setup/developer shapes are conditional boundaries rather than proof that ordinary setup currently returns null world. Reconcile supported transport states, tokens and display contracts with their owners; do not add snapshot/constant tests for each style or DTO field.

## Test direction and scope triage

Retain useful existing behavior tests, especially query/refetch observation, arrival acknowledgement, backend intent parameters, real failure callbacks, hidden-truth boundaries and Phaser destruction. Strengthen coherent scenarios rather than adding a regression for every WB ID. Five families cover the material gaps: nondefault setup/resume with legal phases and rejected/duplicate intent; one query cache across shell/travel/dev with changed results and identity switching; store/preview failures and pending behavior; nested overlays/keyboard maps with focus lifetime; truthful case/diary display with adversarial names, failed outcomes and multi-round expenditure. The Phaser scale contract needs a meaningful renderer/browser oracle because its current doubles omit the relevant library behavior.

StartFlow currently refetches a constant GameStarted fixture through earlier setup/prologue phases, which can override returned phase transitions and allows local-step tests to pass. Correct the fixture contract before deciding which flow assertions are valid. TravelPrep's old-list absence test must not veto a keyboard-accessible destination selector. TownLayout's mocked Set tests conceal the Prepped-only phase restriction; move them with the accepted feature or retire them if deferred. ConfirmDialog has useful busy/Escape/backdrop negatives, but isolated mounting does not protect stacked dismissal/focus restoration. Existing prose and route/style detector assertions must not force invented truth, product chrome or obsolete implementation shapes to survive.

Feature removal must follow the accepted retain/fix versus remove/defer decision, including unrelated-criminal case/poster consumers and historical compatibility already recorded in the Domain audit. Public login/ownership/server resume remain work in the cloud specification; localStorage is only the present selected-session marker and must never become proof of authorization. Do not add cross-tab synchronization, speculative profile features, generic UI infrastructure or a wholesale FSD conversion during this audit.
