# Tests that preserve the wrong baseline

**Status:** Investigation follow-up, not authorization to edit tests or application code. This document connects the [Application findings](2026-10-07-application-layer-investigation.md) and earlier structural findings to concrete test dispositions and intended behavioral coverage. No suites or services were run.

## Remediation rules

- Distinguish a test that asserts an unwanted result from one that merely fails to expose a defect. A green happy path is not automatically protecting a bad behavior.
- Keep useful fixtures and independent behavior assertions. Rewrite the misleading assertion or strengthen the scenario rather than replace every test file.
- Add coverage only for a genuine behavioral gap. A fix does not automatically warrant a new regression test; extend an existing scenario or table when it observes the same boundary.
- Arrange an independent precondition and oracle. Replay must start from immutable genesis/events rather than an already-mutated case; retry must load fresh competing state; HTTP preparation must succeed before its outcome can prove anything.
- Test expected rejection as well as success, including unchanged committed state on rejected commands where that is the intended contract. A failed gameplay action can legitimately produce events; do not impose universal zero-event failure.
- Consolidate fragments of one scenario without merging distinct aggregate, HTTP, PostgreSQL recovery and browser consumer boundaries into a giant test.
- Pure relocation and comment correction generally need compiler/typecheck and consumer verification, not new filename, namespace, method-name or property-existence detectors.
- Keep unresolved public-knowledge, history, conflicting-start and generator contracts conditional until the user agrees their behavior. Do not encode an audit suggestion as a domain rule.

The developer prep/inject/start lifecycle is retired; AP-01, AP-03, AP-05, AP-06 and the prepped-state part of AP-07 no longer call for implementation or tests.

3. **Player read truth:** Strengthen the existing setup-to-start projection flow, meaningful history scenarios and persisted audit metadata boundary. Do not add one test for every DTO field.
4. **Conditional contracts:** Settle public affiliation, historical evidence, store trust and generator semantics before asserting a new rule. Account-isolation/concurrent creation proof belongs to that later authorized feature, rather than preserving a global single-player policy.
5. **Structural cleanup:** Retire obsolete detectors alongside the rejected surfaces. Preserve independently owned validator negatives, actual wire/render behavior and compiler/typecheck proof. Comment edits and pure file moves have no standalone runtime regression requirement.

## Limits and integration cautions

All assertions and skip behavior above were inspected statically. No test pass, runtime failure, restored endpoint or executed concurrency interleaving is claimed. The earlier full test inventory remains the exhaustive audit; this follow-up rereads relevant tests and fixtures for the source findings.

The normal PostgreSQL API factory does not explicitly select Development, while the denial factory selects Production. The acceptance client's `Test` Authorization header is not authentication under the current environment-only guard. When developer workflows are activated, choose the host environment explicitly and prove actual access semantics; do not infer authorization from fixture names.

Fixed `[Fact(Skip=...)]` tests remain inert even with healthy PostgreSQL. Replace obsolete payload fields and invalid seed scaffolding before enabling retained scenarios. Configure required CI dependencies explicitly; do not convert a required test lane into passing skips. Keep optional local dependency limits truthful.
