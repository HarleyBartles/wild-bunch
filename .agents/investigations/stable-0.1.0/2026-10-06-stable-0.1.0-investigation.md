# Stable 0.1.0 investigation and findings

**Status:** Historical investigation record. The interactive audit and its findings have been reconciled into the accepted [baseline specification](../../specs/2026-10-07-stable-0.1.0-baseline.md) and [cleanup roadmap](../../roadmaps/2026-10-07-stable-0.1.0-cleanup.md). This document preserves what was assessed and the evidence available at the time; it is not a live work tracker or an active procedure. Current scope and order come from the specification and roadmap, and each implementation plan is written just in time against the then-current repository.

**Original goal:** Agree a concrete engineering baseline for the first development release, identify what obstructs it, and turn accepted findings into bounded remediation plans. An incomplete pre-alpha can have a deliberate, maintainable release baseline without claiming complete gameplay or production stability.

**Programme handoff:** The accepted [baseline specification](../../specs/2026-10-07-stable-0.1.0-baseline.md) records the settled cleanup boundary; the [roadmap](../../roadmaps/2026-10-07-stable-0.1.0-cleanup.md) records delivery order. The [investigation entrypoint](README.md) distinguishes historical source assessments from current plans. Findings remain evidence, not permission to repair every partial feature; an included feature must work and an excluded half-built feature must get out of its way.

**Context:** [Cloud playability specification](../../specs/2026-10-06-cloud-playability-and-releases.md) and [roadmap](../../roadmaps/2026-10-06-cloud-playability.md). The earlier blocked versioned-release-foundation draft was superseded by the accepted baseline specification and cleanup roadmap; its implementation checklist did not define this investigation's baseline.

## Investigation method used

- The audit read each selected file in full and followed dependency or authority references needed to understand the selected work; the file-specific assessment records its scope.
- The assessment read applicable [unslop profiles](../../unslop/README.md) in full and compared source with domain and repository authority rather than judging names or file size alone.
- Findings record recognition cues, affected paths and consequences, distinguishing confirmed defects, recurring agent patterns, maintainability or harness limitations, missing features and unresolved design questions. A concern could obstruct the baseline without being slop.
- Findings and proposed corrections were discussed with the user. Audit authorization did not authorize automatic sanitization; changes retained by the user are recorded with their actual state below.
- Agreed observable acceptance was carried into the baseline specification and roadmap. Passing tests, a proposed version number or a profile inventory do not define stable.
- Distinct recurring incidents and guard outcomes were added to [unslop observations](../../unslop/observations.md) where warranted; multiple entries or comments about the same underlying work were not treated as independent recurrence.

## Reconciled findings and later delivery notes

**Documentation custody:** [The six non-ADR docs assessed in full](2026-10-06-docs-custody-investigation.md) are tracked as F-005. Five chiefly prescribed contributor policy/procedure and duplicated or bypassed agent owners; `local-postgresql.md` has a legitimate human setup-guide purpose with embedded shared-service rules. The successor disposition retains the PostgreSQL guide, retires the five duplicate or unaccepted proposals, updates frontend doctrine, and records the historical reasoning in the linked assessment.

**Command-bus ownership and discovery (F-006):** The user clarified the intended boundary: `tools/` owns the repository command bus; `scripts/` holds repository scripts with a justified reason to remain outside it. Prefer integration into the bus where meaningful. My initial folder assessment missed this ownership and incorrectly recommended consolidating both roots. The AOM command-bus definition explicitly places the CLI under `tools/` and recognizes `scripts/` for standalone work. That distinction is intentional; roadmap row 03 owns the remaining implementation assessment, written against the then-current source.

At investigation time, routed guidance advertised `tools/run.py` as the CI runner but did not identify command-bus ownership, and the operating-standard subscription and certification contained no `command-bus` entry. The installed AOM definition was read for comparison, not treated as adopted authority. The roadmap assigns explicit adoption, pinning, certification and routing to row 03; this paragraph preserves the original discovery rather than instructing current agents to perform that work outside its JIT plan.

**Agreed cleanup requirement:** Adopt and certify the existing command bus against an explicitly selected immutable AOM definition. Assess and correct its interface before claiming conformance, record the subscription and truthful certification, and make command-bus ownership discoverable from applicable contributor, lifecycle and scoped guidance. The audit identified that the then-current CLI defaulted a selected target without a mode to check and converted subprocess failures to exit code 1; the pinned definition required an explicit selected-target mode and preservation of exact exit status. Roadmap row 03 owns reconciliation against the current pin and source; these historical findings are not a live implementation checklist.

**Test custody:** Python command-bus tests belong with the command bus, keeping that tooling suite separate from application test projects. `scripts/tests/test_run.py` currently tests `tools/run.py` from outside its owner; the same suite also covers scripts, hooks, CI and agent assets. Classify those tests by actual ownership before moving them. `tools/tests/` is the natural proposed home for command-bus tests; standalone script tests can remain under `scripts/tests/`. The explicit pytest invocation and skill-authoring guidance will need corresponding updates for any agreed move. The history explains how the current mixed suite accumulated but does not justify its ownership. No implementation, subscription, routing or test relocation has been performed for F-006.

**Redundant language entrypoints (F-007, agreed anti-pattern):** Do not ship Python, PowerShell and shell variants merely to claim portability. Python already supplies the portable implementation. Remove thin `.ps1`/`.sh` launchers around Python and route callers to the canonical Python entrypoint or command-bus target. Where genuine PowerShell and shell requirements justify native implementations, retain those and remove any redundant Python variant. Assess actual requirements rather than deciding from extensions alone; a command bus may dispatch to a native implementation without creating another copy of its behavior.

Concrete cleanup candidates are `scripts/ci-preflight.ps1` and `.sh`, which only invoke `tools/run.py ci --check`, and `scripts/image_asset_pipeline.ps1` and `.sh`, which invoke a Python compatibility wrapper that itself delegates to the asset-local Python implementation. Assess whether the root Python compatibility wrapper has a continuing caller contract before retiring it. `scripts/dev-servers.ps1` and `.sh` contain actual native process-management implementations (Windows CIM/process trees and Bash signals/background launching); they require a requirements assessment rather than automatic wrapper deletion. `tools/postgres-dev.ps1` also needs assessment against its Windows shared-service purpose, not an invented cross-platform sibling.

The existing `scripts/tests/test_script_entrypoints.py` requires paired filenames for every listed operational script, actively preserving the rejected blanket policy. `test_power_shell_wrappers.py` also freezes the image wrapper's existence, and its invocation test captures a result without asserting successful help behavior. Remove obsolete existence detectors with the wrappers, preserve meaningful behavior coverage at the surviving owner, and update caller guidance. Carry the portability rule into applicable command-bus/script guidance and unslop guards during remediation. No wrappers, tests or guidance have been changed for F-007.

**API folder ownership (F-010, assessment and proposed disposition):** All tracked files under `src/WildBunch.Api` were read in full. `Games` and `Dev` are reasonable API groupings for player operations and developer controls; they describe audiences/use cases, not separate bounded contexts. `Games/Requests` owns player HTTP input contracts and `Games/Validation` owns transport validation. `Exceptions` holds cross-cutting HTTP exception translation, and `Properties` holds conventional .NET launch settings. None needs removal merely because it contains few files. Build-generated `bin` and `obj` are not authored architecture.

The split is not repeated throughout the solution: Application has `Games` and `Dev`, Domain organizes shared game concepts under `Game` and other domain folders, and Persistence owns `GameSessions`. Preserve each layer's actual responsibilities rather than imposing folder symmetry. Keep the current API audience split unless a concrete naming ambiguity warrants a change; finer feature grouping can remain inside each audience.

Concrete follow-up concerns are the 585-line `DevEndpoints.cs` combining session lifecycle, audit, travel, saloon, difficulty, entropy and layout controls; developer endpoint request DTOs owned by `Application.Dev.Models` while player request contracts are API-owned; and prep/start handlers under `Application.Games.Commands` whose only source callers are developer endpoints. Decide whether those lifecycle operations are genuinely shared application capabilities or developer-only use cases before relocating them. Prefer cohesive developer endpoint groups composed by `MapDevEndpoints`, not a new folder for every file.

`Games/ProjectionEndpoints.cs` directly loads sessions/event streams and invokes projectors, giving the transport layer read orchestration that belongs in Application. This is a layer-ownership concern rather than evidence against the `Games` folder. Separately, `MapWildBunchApi` unconditionally maps developer routes and developer services are registered unconditionally; `DevRoleGuard` checks only the Development environment and implements no role. Folder separation therefore does not implement the agreed public/preprod boundary. Align actual composition/access behavior with the cloud specification in its authorized slice. These are static findings and proposed dispositions; no source files were changed or runtime behavior validated.
