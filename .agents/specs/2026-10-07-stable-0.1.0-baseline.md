# Stable 0.1.0 engineering baseline

**Status:** Programme direction and design approved on 2026-10-07. Implementation proceeds under the user's active Stable 0.1.0 goal through the JIT sequence in the [cleanup roadmap](../roadmaps/2026-10-07-stable-0.1.0-cleanup.md). Record settled decisions here rather than relying on conversation context.

## Outcome

Produce a stable `0.1.0` development release that we can build on. Features included in that release work through their real player or developer entry points, preserve their invariants, survive supported persistence and replay, and have meaningful behavioral coverage. Half-built features that cannot meet that boundary are removed from the live release scope and recorded for later implementation. Feature completeness, a finished hunt, public hosting and an availability promise are not release requirements.

Stable means a truthful, maintainable engineering base with a deliberately limited product surface. It does not mean preserving every endpoint, enum, component, test or historical implementation. Nor does it mean accepting broken behavior merely because the game is alpha. We can ship a smaller incomplete game; we cannot describe an unreachable or snapshot-only shell as a working feature.

This specification governs the first workstream of the [cloud roadmap](../roadmaps/2026-10-06-cloud-playability.md). Account isolation, hosted developer isolation, containers, infrastructure and cloud promotion remain subsequent work under the [cloud specification](2026-10-06-cloud-playability-and-releases.md). A local `0.1.0` baseline cannot be deployed publicly until those access boundaries exist.

**Delivery decision, 2026-10-07:** This epic integrates through PRs into develop, initially cut from current main. Each JIT plan takes a fresh canonical worktree from refreshed develop, carries successor-slice retirement of eligible predecessor planning artifacts already in that base, and advances the shared development version once per merged PR. Preparation uses v0.1.0-dev.1; subsequent merges use dev.2, dev.3 and onward. `Directory.Build.props` is the sole authored application version. The web build derives its runtime build identity from effective MSBuild evaluation; the private npm package and lockfile do not carry duplicate application versions. Build outputs are generated, not committed. The first JIT delivery completes version consumption and validation rather than postponing version ownership until qualification. The roadmap owns the detailed delivery contract. Keep the active epic spec/roadmap and each current plan through its completing PR; develop collectively becomes the qualified 0.1.0 prerelease candidate, not a final release merely by receiving a merge.

## Disposition before remediation

Every finding and feature claim receives an explicit disposition before its affected implementation plan is accepted. Preserve the investigation IDs and link grouped findings to their owner; one underlying behavior can cover several findings without creating one ticket or test per finding.

| Disposition | Meaning and required treatment |
| --- | --- |
| Retain and repair | A release capability with a coherent promise. Repair its actual command/read/player path and tests; name supported failures, resume and replay. |
| Retire and defer | A partial or unnecessary capability excluded from 0.1.0. Remove its live producers, availability, consumers and misleading claims; preserve shared behavior, selected historical support and a separate future-addition story. |
| Consolidate | Competing owners, duplicate mechanisms or fragments of one behavior. Select one authority, move consumers and transfer useful coverage. |
| Historical support only | A retired producer still has supported persisted facts. Keep or migrate the necessary readers/effects without making the feature available again. |
| Correct guidance or history | A stale claim, implementation-heavy ADR or ineffective route. Repair current guidance and preserve truthful historical decisions and deviations. |
| Explicitly defer | A nonblocking concern with its consequence and owner recorded. A defect in an included feature's required invariant cannot be hidden in this category. |
| Investigate or decide | Evidence or a consequential decision is missing. Name the exact uncertainty and block only the dependent plan; do not invent product intent. |

**Existing-behavior decision, 2026-10-07:** Preserve current implemented behavior and numerical values where they are coherent, satisfy the agreed invariants and do not conceal an unfinished feature. Record the inspected rule and its behavioral proof without seeking approval for each value. Raise a question only for a consequential conflict, missing behavior or scope choice. This is not permission to preserve bugs or accept tests that protect incorrect behavior.

No material audit finding may disappear through a file move or feature removal. The roadmap must account for the top-level F findings, ADR dispositions, test-quality dispositions, AP-01 through AP-20, PS-01 through PS-17, DN-01 through DN-16 and WB-01 through WB-24. Coverage means an accepted remedy, justified retirement, selected history treatment or explicit nonblocking deferral, not a checked box asserting the audit was read.

Each roadmap row links its finding groups and declares an observable exit. Before accepting its plan, identify which existing tests protect the wrong state, which useful coverage transfers, and what genuine behavioral gap remains. A source correction, its test correction and relevant current-truth updates form one deliverable; a later test-cleanup row cannot excuse shipping the newly corrected behavior without proof.

## Product boundary

A feature is an observable capability with a coherent lifecycle, not a folder, endpoint or type. Player features, developer capabilities and platform requirements remain distinct. The durable matrix will live at `docs/features.md`, with one authored authority and lifecycle routes requiring contributors and reviewers to read and update it when a product promise or dependency changes. Its initial publication is a reconciliation task, not copying the working inventory and labelling everything shipped.

Each matrix entry needs a stable ID, audience and promise, actual entry point, prerequisites, supported outcomes and failures, resume/history contract, implementation assessment, release disposition and directed dependencies. Dependencies state whether a capability requires another capability, consumes its output or changes its state, including conditional prerequisites. Record static assessment separately from runtime evidence. Retired features retain a removal record linked to a distinct future-addition record.

**First-arrival command decision, 2026-10-07:** Starting-town selection is a one-shot player action. Selecting a valid town commits the choice and free first arrival together; the player is then in that town. There is no second selection, intermediate player confirmation or route to choose another starting town. Subsequent movement uses ordinary travel. Selection/arrival events may describe constituent facts, but they commit as one logical command outcome without duplicate resource grants or partial visible progression.

After arrival, the starting-town action is unavailable and new starting-town commands are rejected, including commands naming the same town. Handling a retransmission of the same already committed operation is transport recovery, not another legal player action. Where such recovery is supported, it identifies that original operation and reports its established outcome without reapplying effects; matching town arguments alone do not make a new command a retry. **Resource floor and death decision, 2026-10-07:** Item quantities and remaining usable charges cannot fall below zero. Gameplay losses consume at most what remains; the authoritative event, inventory/journey state, projection and narration record the actual loss rather than a nominal amount that could not be taken. Multiple losses within one day resolve against the progressively remaining resources. This does not turn invalid purchase quantities or malformed authoritative history into silently accepted inputs; reject invalid intent/history under the owning contract.

Food shortage is included in 0.1.0: each trail day without a meal incurs a 25 HP health toll. This is the initial 0.1.0 value; later balancing may change it through the normal release process. Use the existing daily-upkeep boundary: available food at that day's upkeep feeds the player and consumes one unit; consuming the last unit feeds that day. A day starting upkeep with no food incurs the toll once. Losing remaining food later in that day affects the next day's meal rather than charging another daily toll. Refresh, preview, pending encounter choices, command retry and replay do not charge another day. Use 25 HP for every unfed trail day without adding a difficulty-dependent starvation table. If less than 25 HP remains, the actual loss reaches zero and records death.

Zero HP means player death from any implemented cause, including food shortage, running and fighting. Health loss stops at zero; death is an event-backed terminal failed playthrough, not a UI-only consequence. Record the final health and terminal transition in the same committed operation; replay reconstructs death without RNG or re-executing commands. A lethal upkeep/action cannot continue into later encounters, arrival success or rewards. Dead sessions reject further gameplay mutations, remain readable/resumable to their terminal state, and allow confirmed start over. No new saloon gunfight, revival or hunt-win mechanic is introduced. Protect last-food versus unfed days, cumulative losses, lethal and over-lethal damage from real retained paths, terminal command rejection, fresh-load/replay and truthful death display with independent behavior assertions.

## Architecture and state invariants

Preserve the selected DDD, strict CQRS and event-sourcing posture. `GameSession` remains the live gameplay aggregate boundary. Internal children own cohesive state and rules, accept narrow context, and return outcomes/events without mutating siblings or owning persistence. Do not create child repositories, a generic NPC framework or a new event-store platform to perform cleanup.

Commands validate intent and establish facts through typed events. Event application reconstructs recorded facts without sampling randomness, using the current clock or consulting mutable content to replace established history. Application orchestrates use cases, fresh-state retries and safe mapping; gameplay legality belongs in Domain. API maps transport. Persistence appends/stores/reconstructs and owns envelopes and schema, not gameplay rules.

Queries use their supported read ports and player-safe models, without gameplay mutation, event creation or gameplay commits. Cache reconstruction is infrastructure work and cannot invent game facts. Command responses can legitimately return safe read DTOs after commit. Unknown setup values remain unknown; mappers, narration and UI must not fill them with fictional locations, health, provenance, ranking or successful outcomes.

Recorded generation, preparation, salt changes, inventory effects and phases must be reconstructible from the accepted history boundary. Retire the exclusive zero-event developer prep/start route. Any independently retained preparation must be event-backed; normal player creation must have replay-complete genesis. Existing exceptional data is handled explicitly under historical policy.

Retries reload authoritative state and repeat decisions against that state; neither a fake returning the same mutated object nor generation outside the retry proves safe concurrency. Illegal, contradictory or stale intent is rejected according to the actual contract, never silently coerced into a different successful command. A committed phase transition removes actions that are no longer legal. A lawful unsuccessful action may consume time/resources and emit events; do not impose a universal failure-means-no-change rule.

Snapshots, component rows and projections are reconstructible caches for event-backed sessions. Version equality, JSON validity or a nonempty row set does not prove validity, completeness, freshness or a coherent stream position. Correct reads and command loads must converge from intact history when supported caches are stale, missing, partial or malformed. Unrecoverable history fails explicitly instead of creating replacement entropy or defaults. Handle known database append constraints specifically; unrelated uniqueness failures must not masquerade as concurrency conflicts.

## Cache-backed state and recovery

**Settled 2026-10-07:** Immutable event history continuously maintains derived state; commands and queries use the appropriate current derived representation in normal operation. Invalid derived state is rebuilt from events and consumers resume through the same state/read ports. The [fresh architecture spike](../investigations/stable-0.1.0/2026-10-07-cache-state-architecture-spike.md) supports this pattern. Full replay is the invalid-cache recovery strategy, not the normal cost of every request. Incrementally maintaining healthy caches from newly committed events is normal operation, not the retired competing incremental-recovery route.

Keep command-side GameSession snapshot loading distinct from audience-specific query models, in the existing PostgreSQL database. Commit new events and updated current snapshots/projections as one unit of work with expected stream-position concurrency. Only committed facts are visible as successful gameplay. Every load/result uses one coherent stream position; implement coherent transactional reads or equivalent verified retry, not independent unverified queries that mix positions. Caches carry their applied stream position and projection/schema version. Required-component and diary completeness and supported state invariants are checked; matching version numbers alone are insufficient.

Rebuild once from supported, ordered, upcasted authoritative events for the selected position, deriving the needed state and views. Never sample a replacement salt, rerun a decision or invent optional state whose event-established value is missing. Preserve legitimate absence where the selected history establishes it. Publish repair only if it cannot overwrite a newer committed position. An in-memory rebuilt representation can satisfy the same port without a mandatory write-and-reread. Persistence writeback is derived maintenance, not a gameplay mutation; queries must not issue commands, emit game events or advance gameplay. Invalid authoritative history fails explicitly with recoverable player-facing load failure; it is not silently skipped, guessed or automatically replaced by a new game.

Use the production loader/serializer/rebuild boundaries for tests. Preserve event upcasters, but remove inert projection-upcaster and dormant competing partial-replay scaffolding. Changed projections rebuild from history. Prove valid-cache and invalid-cache paths against independent expected facts and the next legal action, including partial diary/component loss, stale/current malformed payloads, legitimate optional absence, concurrent read/write interleaving and repair racing a newer commit. Replay and fast-path equality alone can preserve the same bug and is not sufficient proof.
