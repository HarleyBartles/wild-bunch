## Delivery sequence

### Develop integration and per-plan delivery

The user selected Gitflow for this entire epic on 2026-10-07. The integration branch is `develop`, cut from current `main`; `develop` is the repository's default branch and normal base for development PRs, while `main` is reserved for explicit releases and hotfixes. Every JIT implementation plan starts in a fresh canonical worktree from refreshed `origin/develop`, with a dedicated `codex/` branch. Author and commit that plan in its worktree, execute it inline under the authorized goal, and deliver the implementation by PR targeting `develop`. Do not reuse the preceding plan's worktree, branch from stale main, or integrate implementation by direct push. The preparation branch begins at the same main commit as develop and supplies the spec/roadmap bootstrap by PR; subsequent plans require that preparation to be merged first.

Before moving to the next plan, verify the preceding PR actually merged into `develop` and that its committed output passed the required review and validation. Refresh develop and inspect the merged implementation before taking the next fresh worktree. If an outcome needs several bounded plans, each gets its own worktree and PR under this rule. Plan readiness does not imply permission to merge without satisfying review/checks; preserve actual goal authorization for merge and publication.

Each PR also performs successor-slice retirement through [completed-artifact doctrine](../doctrine/completed-artifacts.md) and the [completing-plans playbook](../playbooks/completing-plans.md), using current `develop` as the successor base for this epic. Inspect prior planning artifacts semantically against the implementation and merged delivery, promote enduring decisions/guidance, then retire only wholly completed or explicitly abandoned predecessor artifacts present in that base. Remove stale links in the same successor PR's first substantive commit. Keep the current plan through its completing PR so squash merge preserves it in canonical history. Keep this roadmap, its specification and any mixed/live investigation scope while they still govern the epic. When there is no eligible predecessor, preserve the artifacts rather than manufacture a deletion. No tracked archive or cleanup-only PR is required. At the end of this epic, its last plan and parent artifacts remain until a qualifying substantive successor retires them.

### Development version identity

The epic's intended release foundation adopts AOM `gitflow` and `semver`; row 18 writes the JIT adoption plan, pins the accepted immutable definitions current at that time, and implements repository-owned certification and durable routing. Develop accumulates `v0.1.0-dev.1`, `v0.1.0-dev.2`, `v0.1.0-dev.3` and subsequent monotonically increasing development versions. This preparation PR reserved dev.1. `Directory.Build.props` owns the only authored application version. The production web build derives a generated `version.json` identity from effective MSBuild evaluation; this output is not committed. The private npm package and lockfile omit duplicate application version fields. Tool-facing version syntax is `0.1.0-dev.N`; the `v` prefix is a human/tag label. Dependency package versions are unrelated and must not be bumped as part of this policy.

Every subsequent ordinary PR merging to develop, including documentation and tooling, reads the latest merged version and assigns one unique next N in `Directory.Build.props`; the build regenerates the web identity from that authority. Increment once per merged PR, not per commit, review repair or CI retry. Before merge, refresh the base and reconcile the proposed successor number; if another PR merged first, update the authored version and rerun affected review/checks rather than merge a duplicate or out-of-order identity. A failed or unmerged PR does not consume a number. Each JIT plan names the version owner and generated identity check explicitly.

The first JIT outcome establishes the check-only commit/CI behavior before any implementation commit relies on it, then completes generated build-identity consumption and validation around this preparation's version authority; it does not leave duplicate authored product versions until row 18. The production web build generates the identity, and the canonical command bus checks the generated result. This first slice uses the current bus narrowly; row 03 later completes command-bus adoption/certification and script rationalization, while row 04 delivers lint/style and post-edit formatting. This ADR/guidance successor refreshes the tracked-hook standard pin to its current no-mutation definition; hosted Linux parity remains subject to the non-draft PR gate. Later command-bus work preserves that contract and verifies the pin remains current. Later changes preserve the single version authority. No tag or GitHub Release is automatically created for every develop merge. Develop becomes the collective 0.1.0 prerelease candidate as the roadmap exits are delivered; row 18 qualifies that source before the separate release-branch/main/tag/merge-back procedure. Qualified changed candidates use `0.1.0-rc.N`; stable promotion uses the exact verified source and stable version. The current `0.y.z` policy explicitly makes no public API or gameplay-compatibility promise and may allow breaking changes. No future `1.0.0` contract is required or decided in this epic; define and publish it when preparing that release. Do not stamp final `0.1.0` while cleanup is incomplete.

Rows are delivery outcomes, not prewritten plans or a promise of exactly eighteen commits. A broad row may require several consecutive bounded plans.
