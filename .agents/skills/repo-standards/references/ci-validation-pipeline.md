# CI validation pipeline

Every repo that uses `repo-standards` supplies its own canonical validation
capability and declares how that capability composes the checks CI runs for
that repo. This reference describes the contract, not a command name.

- The consumer's apply capability may materialize mechanical surfaces only.
- The consumer's check capability is the fail-fast CI/PR gate; its diagnostic
  mode may report independent failures before exiting.
- The tracked `githooks/pre-commit` hook, activated with
  `core.hooksPath=githooks`, is the single complete local gate for a normal
  commit. It materializes the staged snapshot, applies mechanical surfaces,
  stages only owned generated surfaces, then checks that snapshot before
  allowing the commit.
- CI runs the same canonical check capability in a fail-fast workflow.

## Consumer preflight

The consumer's canonical check is the full non-mutating CI/PR gate. It runs the
declared checks in their repository-defined order and stops at the first
failure, unless its diagnostic mode is requested.

Run the smallest focused checks that prove the slice while iterating. For a
normal commit, stage the intended tree and let the tracked pre-commit hook be
the complete local gate.

## Pre-commit hook

The hook is generated by the consumer's repository-standard implementation and:

1. marks the execution with `REPO_STANDARDS_STAGED_SNAPSHOT=1`;
2. preserves and hides all unstaged edits and untracked files;
3. materializes the staged index in the working tree;
4. runs the consumer's canonical apply capability;
5. stages only the owned generated surfaces it produced;
6. runs the consumer's canonical check capability on the exact staged snapshot;
7. restores the user's unstaged and untracked work.

Consumer commands that optimize work by changed paths must use the staged index
when `REPO_STANDARDS_STAGED_SNAPSHOT=1` (for example, `git diff --cached
--name-only`) or validate the complete materialized tree. They must not derive
the candidate change solely from committed `HEAD`, because Git invokes a
pre-commit hook before the candidate commit exists.

If any step fails, the commit is blocked. Do not bypass the hook with
`--no-verify`.

## CI workflow

Hosted CI executes the tracked `githooks/pre-commit` directly from a clean
checkout with `REPO_STANDARDS_HOSTED_COMMIT=HEAD`. The hook reconstructs that
commit as a staged snapshot over its first parent, verifies the reconstructed
tree, and then enters the same path Git uses locally. It does not copy the hook
into `.git/hooks` or depend on local Git configuration. The hook reads the
consumer command declaration, so the same repository-specific apply and check
capabilities remain authoritative locally and in hosted validation.

This is the portable hosted entry point:

```yaml
- name: Validate tracked commit gate
  env:
    REPO_STANDARDS_HOSTED_COMMIT: HEAD
  run: githooks/pre-commit
```

## What to do when a check fails

A failing diagnostic check lists every failing target together with its repair
capability. Run the repair capability for each failing target, then re-run only
that target's focused check to confirm it is green before committing again.

Do not run the complete check immediately before a normal commit or immediately
after a successful hooked commit. The hook already proves the staged tree.

## When to run the complete gate manually

Run the complete check only when:

- no normal commit will follow (a one-shot uncommitted verification),
- you are diagnosing the pipeline and need a complete fail-fast report, or
- you are explicitly proving CI parity.

## Consumer command map

The consuming repository documents the exact apply/check commands, target names,
hook sequence, and any platform-specific wrappers. Portable workers must read
that local command map rather than assuming a path, interpreter, command bus,
or target name.
