# Wild Bunch Project Doctrine

## Owned decision

Establish the repository's source-truth, workspace, policy, and specialist-skill route before substantive Wild Bunch work begins.

## Core posture

- Inspect the live repository before claiming current code, documentation, branch, validation, or publication state.
- Treat task briefs, issue text, chat summaries, reports, and memory as context until the owning system confirms them.
- Work in a dedicated linked worktree and task branch based on current `origin/main`, then use a PR unless the user explicitly authorizes another publication route.
- Preserve explicit scope, non-goals, protected surfaces, validation commands, and return evidence.
- Read `scripts/AGENTS.md` before replacing a repository script with an ad hoc command or reporting missing local tooling.
- Invoke the smallest specialist skill that owns the actual domain, architecture, browser, workflow, or connector decision.

## Workflow

1. Verify repository, worktree, branch, base, and initial status.
2. Read the task's canonical requirement source and relevant local policy.
3. Inspect live source for every current-state claim.
4. Route to the relevant specialist skill and validation owner.
5. Return only evidence the repository, GitHub, Linear, or test output proves.

## Stop conditions

- Stop when repository identity, base, source owner, protected surface, or required authority is ambiguous.
- Do not use this router as a substitute for `wild-bunch-domain-modeling`, `wild-bunch-dotnet-architecture`, or `wild-bunch-browser-game`.
