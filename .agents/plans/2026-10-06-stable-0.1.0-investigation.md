# Stable 0.1.0 investigation and findings

**Status:** Interactive investigation. The user supplies the file set; read each file in full and discuss the evidence before deciding what stable `0.1.0` requires. This document is the live audit and work tracker, not authorization to fix every finding.

**Goal:** Agree a concrete engineering baseline for the first development release, identify what obstructs it, and turn accepted findings into bounded remediation plans. An incomplete pre-alpha can have a deliberate, maintainable release baseline without claiming complete gameplay or production stability.

**Context:** [Cloud playability specification](../specs/2026-10-06-cloud-playability-and-releases.md) and [roadmap](../roadmaps/2026-10-06-cloud-playability.md). The [versioned-release draft](2026-10-06-versioned-release-foundation.md) is provisional follow-on work and cannot define or substitute for this investigation's baseline.

## How we investigate

- Wait for the user's selected files and read every selected file in full. Follow a dependency or authority reference when it is needed to understand the selected work, and state when that expands the investigation.
- Before assessing a concern, read its applicable [unslop profiles](../unslop/README.md) in full. Compare the actual source with current domain and repository authority rather than judging names or file size alone.
- Record concrete recognition cues, affected paths and consequences. Distinguish a confirmed defect, recurring agent pattern, maintainability or harness limitation, missing feature and unresolved design question. A concern can obstruct the baseline without being slop.
- Discuss findings and the proposed correction with the user. Audit authorization does not authorize automatic sanitization. Retain changes already made and explicitly accepted, with their actual state recorded below.
- Track intended observable acceptance for an agreed correction, then assign it to a bounded implementation slice. Do not treat passing tests, a proposed version number or a profile inventory as the definition of stable.
- Add distinct recurring incidents and guard outcomes to [unslop observations](../unslop/observations.md) where warranted; multiple entries or comments about the same underlying work are not independent recurrence.

## Baseline decisions to settle

- Which implemented player flows must behave coherently for `0.1.0`, and which incomplete behavior is deliberately outside the baseline?
- Which authority, event/replay, persistence, projection and browser-state invariants must hold in the selected flows?
- Which tests demonstrate those behaviors and failure cases, and which assertions merely preserve implementation trivia?
- Which structural, naming, ownership or guidance problems obstruct maintainability enough to address before feature iteration?
- Which migration and release checks are required to cut the first baseline, separately from later public hosting requirements?

These are investigation questions, not allegations about files we have not yet read. Record the agreed answers here as the discussion progresses.
