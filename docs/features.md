# Wild Bunch Feature Matrix

**Status:** Current product-scope authority, reconciled on 2026-10-16. This matrix records what Wild Bunch promises, what the 0.1.0 baseline includes, and how capabilities depend on one another. It does not certify that an implementation works merely because a route, component, event, type or test exists.

Use the [feature-matrix playbook](../.agents/playbooks/feature-matrix.md) when a design, plan, implementation, review or release changes a product promise, capability boundary, dependency or evidence assessment. The [current gameplay rules](gameplay.md) explain the retained local rules; this matrix owns capability grouping, disposition, dependency meaning and deferred feature intent. Retired investigations remain immutable historical evidence, not current authority.

## Reading the assessments

**Implementation assessment** describes current source and existing behavior-test evidence. `Coherent` means the assessed path matches its current promise; `partial` means only part of the lifecycle is implemented; `broken` means a required outcome or invariant is known to fail; `unreachable` means no supported player path reaches it; `disabled` means it is deliberately unavailable; `planned` means no current implementation is promised; `not assessed` means evidence has not been traced. A feature may have more than one status across its lifecycle.

**Release disposition** describes whether 0.1.0 retains and repairs the capability, consolidates it into another surface, retires it, or records it only for later work. A retained-but-broken feature remains a product promise and must be repaired; a partial capability is not automatically a shipped feature.

**Evidence** links the source and test investigations that assess the existing behavior. Those assessments are static evidence unless they explicitly report a runtime run. They do not claim a browser playtest, deployed environment or external player validation. The source of game truth is the event history; saved state and projections are reconstructible under the [current history and recovery rules](gameplay.md#state-replay-and-history).

Dependency edges use these meanings: **requires** means the target is a necessary precondition; **consumes** means the source uses the target's output; **changes** means the source changes the target's state or availability; **conditional** means the edge applies only under the stated game state or choice. Shared imports and normal player sequence do not by themselves establish a dependency.

## Player capabilities

### PG-001 - Start a hunt and choose the first town

**Promise and entry:** A new player names the character and starts a hunt from the setup surface. Optional difficulty offers Easy, Standard, Challenging and Brutal, defaulting to Standard; optional randomness offers Boring, Classic, Adventurous and Wild, defaulting to Classic. Difficulty owns pressure/resource policy, randomness owns volatility, and neither changes settled mystery facts. Each visit to setup presents a fresh editable seed UUID, and a supplied seed is validated and used. Starting the game settles the world, gang, identities and culprit. The player then reads the prologue, which contains the case lead, and chooses a starting town on the same world map. Choosing the town is one command outcome and the first free arrival; there is no second choice or journey-time charge. See the [hunt creation contract](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-hunt-creation-contract.md).

**Authority, failure and history:** The server and event history establish setup and phase. The world is settled before the prologue is read; only player location is selected afterward. Acknowledgement advances the current prologue phase and cannot regenerate the case or substitute a different clue. A repeated town selection after arrival is illegal; an actual transport retry may return the original result without reapplying it.

**Dependencies:** `PG-003` is **consumed** for the starting-town choice. A started session supplies identity and settled world state to `PG-002`, `PG-005`, `PG-006`, `PG-007` and `PG-008`.

**Assessment and evidence:** Partial across the complete player lifecycle. Normal setup persists generated world/case facts and recorded salts; event decoding and replay restore them, and prologue acknowledgement advances the same history. Setup validates a supplied seed and supported options; fresh/randomized/edited UUID behavior and Standard/Classic defaults are covered by rendered tests. Startup retries retain the exact operation ID and request, return current event-derived state without duplicate events, and reject changed requests or malformed identity before mutation. PostgreSQL concurrency tests cover one session for exact concurrent deliveries and one active session for distinct setups. Session-scoped prologue reads use the saved case lead and keep hidden culprit internals private. [Startup browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes name-only start, restoration of the prologue, acknowledgement, pointer-operated town choice and restoration of the arrived town through the real local API/PostgreSQL. [Genesis replay](../tests/WildBunch.Integration.Tests/Acceptance/PlayerSetupReplayAcceptanceTests.cs), [startup endpoint](../tests/WildBunch.Integration.Tests/StartupOperationEndpointTests.cs), [startup persistence](../tests/WildBunch.Integration.Tests/StartupOperationPersistenceTests.cs) and [prologue privacy](../tests/WildBunch.Integration.Tests/PrologueHiddenTruthTests.cs) tests cover their distinct boundaries. This bounded local coverage does not establish a complete hunt, every retained route, deployed resume or account ownership.

**0.1.0 disposition:** Retain and repair. Do not bypass the prologue or first-town choice for quick play. A complete hunt-resolution/win flow is not established and is not required to call this deliberately incomplete game 0.1.0.

### PG-002 - Resume, archive and start over

**Promise and entry:** A player can leave and return to the selected game, resume from the server's saved phase, and choose Start Over in Game Settings. One game is active in the current player flow; selecting among multiple retained playthroughs is not a 0.1.0 feature.

**Authority, failure and history:** Browser storage is not game authority. Confirming Start Over commits an archive event before returning to setup; that decision persists if the browser closes, the user signs out, or no replacement game is created. Cancelling changes nothing. Retain archived history; restoration and multi-playthrough discovery are later work. See the [playthrough lifecycle contract](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-playthrough-lifecycle-contract.md).

**Dependencies:** **Requires** an established game from `PG-001`; archival **changes** availability of all surfaces tied to that game. Resume **consumes** event-backed state and persistence/recovery support in `PLAT-001`.

**Assessment and evidence:** Partial. Resume restores the server-owned phase and retains the saved ID/deep link during transport uncertainty; a server-confirmed missing session requires an explicit player action. Start Over reconciles uncertain archive responses with a fresh read: only confirmed Archived state clears the saved pointer, including a retry returning conflict; Active or unreadable results retain it. Reloading an archived session returns to setup without another archive or replacement setup. [Client behavior coverage](../src/WildBunch.Web/src/tests/StartOverConfirmation.test.tsx) covers retries and cancellation; [production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes cancellation without mutation, confirmed archive and subsequent page reopen against the local PostgreSQL-backed API. [Modal browser coverage](../src/WildBunch.Web/browser-tests/modal-stack.spec.ts) separately covers nested focus, inactive background actions and narrow-viewport visibility. These boundaries do not establish cross-tab synchronization, account ownership, archived-game restoration, deployment or the complete player lifecycle.

**0.1.0 disposition:** Retain and repair saved-phase continuation and event-backed confirmed archive. Cross-tab push, account-backed game discovery and restoring archived games are excluded.

### PG-003 - Consult one world map and navigate towns

**Promise and entry:** One world map supports the explicit starting-town choice and later travel, each under its own legal phase rules. Every town visibly contains a Saloon, Sheriff, Store and Telegraph. `TownLayout` is the authority for building presence; available actions are the authority for usability. Saloon, Sheriff and Store actions are available in every town, while the Telegraph remains visible and disabled. Generated town layouts persist between visits; refreshing or replaying does not generate different geometry.

**Authority, failure and history:** The server owns map destinations and legal selection; the browser renders and reports the selected destination. The starting choice is one-shot under `PG-001`; later movement uses `PG-007`. For the 0.1.0 baseline, town selection uses the existing pointer interaction on the shared map; map-level keyboard/screen-reader town selection is excluded by [ADR-0046](decisions/ADR-0046-pointer-operated-town-selection-for-0.1.0.md). Eligible destinations and recoverable map-read states remain part of the player contract.

**Dependencies:** Supplies map selection to `PG-001` and `PG-007`. Town navigation provides entry points to `PG-004`, `PG-005` and `PG-006`; entry does not vary by town service flags or make later travel depend on setup.

**Assessment and evidence:** Partial. One pointer-operated map serves starting-town choice and later travel under ADR-0046. Map-host behavior coverage addresses live selection, travel eligibility and responsive town/trail geometry; town-hub coverage addresses fitted sprite hover/restoration, rectangle fallback and building selection. [Town-layout generator tests](../tests/WildBunch.GameContent.Tests/NewGame/TownLayoutGeneratorTests.cs) cover required services across supported palettes/prosperity, road/building geometry and complete same-input determinism; they do not establish persisted repeat visits. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes starting-town selection, connected-route departure/day/encounter paths and completed-trip acknowledgement/restoration. [Browser fixture hover coverage](../src/WildBunch.Web/browser-tests/town-hub-hover.spec.ts) addresses fitted artwork restoration in the real Phaser scene through a Vite-served fixture; it is separate from the production-game routes. These are bounded map/town routes, not every map path or deployed behavior; PG-007 owns travel limits. The [historical Web architecture assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-web-architecture-spike.md) records the earlier boundary.

**0.1.0 disposition:** Retain one shared world map and usable town navigation with pointer-operated selection. Do not add map-level keyboard/screen-reader town controls, separate start and travel map authorities, or a town-layout editor.

### PG-004 - Buy supplies and manage player resources

**Promise and entry:** A player buys the currently supported supplies from the one Store available in every town. The store's stock and the price of each offered item vary with town prosperity. Equipment is unique by item type; consumables can stack. A player cannot acquire a second horse or canteen without benefit. When a horse dies, it leaves inventory and the saddle remains. Arrival refills a canteen only when the player owns one.

**Authority, failure and history:** Purchases and losses change event-backed wallet/inventory state. Counts and remaining charges never fall below zero; loss records the actual quantity removed. Invalid purchase intent is rejected. Detailed stock, price and fine values remain in the [baseline specification](gameplay.md) and [store/inventory contract](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-store-and-inventory-boundaries.md).

**Dependencies:** **Requires** an active game and a town Store. Purchase output **changes** inventory and wallet state consumed conditionally by `PG-006` and `PG-007`. Town prosperity **changes** store stock/prices; distinct vendor identity does not.

**Assessment and evidence:** Partial. The one-store catalog, prosperity-tier stock/prices and item-only purchase contract are implemented across Domain, Application, HTTP and browser boundaries. Horse death removes the horse while retaining the saddle, and arrival refills only an owned canteen. The current firearm capability is revolver-only; unsupported Rifle/Rifle-ammunition paths are absent, with the complete addition deferred as PG-004-B. The forward-only pre-alpha invalidation migration preserves schema and migration history while permitting new sessions. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes a real Food purchase using the offered price, exact wallet/inventory change and restoration after reopen without another purchase. Other catalog tiers, rejection paths, the complete travel-resource lifecycle and deployed behavior are not established by that route. The [historical store/inventory assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-store-and-inventory-boundaries.md) records the original boundary.

**0.1.0 disposition:** Consolidate to one Store and repair. Preserve coherent existing item/pricing behavior by prosperity; distinct stable, gunsmith and other vendor services are future features.

### PG-005 - Gather public investigation knowledge

**Promise and entry:** The player can learn from the prologue lead, wanted posters read from the Sheriff Office context, reachable saloon gossip, and saloon observation. Each wanted-poster read reveals one clue. There is no town noticeboard, public-square interaction, sheriff-records interaction or privileged case-record access in 0.1.0. An observed person is evidence about a distinguishing feature, not a solved identity. The player draws conclusions from the facts collected.

**Authority, failure and history:** Learned claims preserve their actual text, source, identity only when explicitly established, and recorded time/place details. Unknown subjects remain unknown. Reading a source records only the knowledge/outcome the player actually received. A wanted poster may identify gang affiliation only when its public warrant terms state it; internal target kind, culprit identity and pressure-routing metadata remain private. The opening culprit clue is sourced to the Prologue. Telegraph remains visible but disabled and has no 0.1.0 command, route or generated clue source.

**Dependencies:** **Requires** an active game and the relevant town/source context. Produces player-known facts **consumed by** `PG-006` and `PG-008`; source availability and return-visit refresh are affected conditionally by `PG-007`.

**Assessment and evidence:** Partial. Prologue knowledge, Sheriff Office wanted posters and saloon gossip are supported; saloon observation/named take-in is assessed under PG-006. Generated-case, Domain and API coverage addresses opening-clue provenance, privacy and removal of unsupported Telegraph, noticeboard and sheriff-records interactions. [Wanted-poster acceptance coverage](../tests/WildBunch.Integration.Tests/Acceptance/WantedPosterAcceptanceTests.cs) exercises persisted public journal state and hidden-truth safety. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes reading a public poster and restoring it after reopen without another read, plus gossip whose learned clue and authored journal entry retain LocalGossip provenance after a fresh journal read. These routes do not establish every knowledge source, hosted behavior or deployment. The [historical Application assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-application-layer-investigation.md) records the earlier source boundary.

**0.1.0 disposition:** Retain and repair the prologue, Sheriff Office wanted posters, saloon gossip and observation. The thin noticeboard and fake sheriff-records surfaces and their authored public-notice clue are removed; the two redundant telegraph gang clues are removed and telegraph remains unavailable pending the lawman feature. Do not add an automatic deduction engine. ADR-0024 preserves the accepted source-specific variation rules as constraints on future implementation, not evidence that those mechanics exist; no newspaper interaction is included in 0.1.0.

### PG-006 - Name and take in a saloon person

**Promise and entry:** In a saloon, the player may look around and see a person described by distinguishing features. A take-in attempt requires the player to name the person; suspicion or a matching clue alone is not enough. A citizen comes quietly, is released by the sheriff, and incurs the existing $10 fine capped at available cash. A wanted person requires the player to own a gun to compel a take-in; ammunition is not required. A wrong name releases the person, pays no bounty and gives no gang-roundup credit. A correct name can pay the bounty and count that distinct gang member toward the five-of-six culprit-release gate in the seven-member gang.

**Authority, failure and history:** The server validates current saloon presence and naming. Outcomes, fine and bounty are recorded through the event-backed game session and reconstruct through replay. The culprit's identity is settled at game start; lawful settlement of five distinct other members of the seven-member gang releases the already-known culprit into encounter eligibility. Killing the culprit would fail the hunt while leaving corpse bounty payment possible, but no kill flow is implemented in 0.1.0.

**Dependencies:** **Consumes** relevant learned identity/public information from `PG-005`. Lawful outcomes **change** wallet, case and culprit-release state consumed by `PG-008`; player equipment from `PG-004` is a conditional prerequisite for taking in wanted people. The interaction does not require or establish `PG-009`.

**Assessment and evidence:** Partial. Observation and named take-in use the player saloon command. Blank names preserve the observed person; citizens cooperate with the wallet-capped fine; wanted people require a gun but no ammunition; wrong names pay no bounty/roundup credit, and gunless refusal does not record flight. Five distinct lawful non-culprit gang settlements open the encounter gate; four do not. Progress derives from settlement facts and warrant classification and survives event replay/PostgreSQL reload. A public poster may identify the culprit while the saloon gate remains closed; player DTOs and journal omit the culprit flag/release counter. Command, replay and persistence coverage includes citizen/wrong-name/refusal/repeat negatives and poster discovery. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes poster restoration, matching saloon observation, explicit naming and secured-living bounty settlement; it does not establish browser negatives, a full five-of-six journey, deployment or overall completion. The [historical saloon clarification](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-saloon-challenge-contract.md#2026-10-10-current-010-clarification) and [culprit contract](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-culprit-identity-and-release-contract.md) preserve supplied intent.

**Robustness limits:** Saloon selection covers a valid runtime-shaped salt folding to the minimum integer and preserves selected identity/kind through command/replay. Pure CitizenCast role/feature selection also covers extreme accepted hash inputs; this does not establish that normal play reaches those visit counters. Negative wallet cash, bounty/settlement values and persisted negative settlement events are rejected while zero remains valid. These are accepted-input and event-ingress contracts, not evidence of negative authored content in ordinary play.

**0.1.0 disposition:** Retain and repair named take-in, citizen/wanted distinction, correct/wrong-name settlement and the five-of-six release gate. Resistance rolls, escape/injury, saloon gunfights, sheriff poster circulation and murder consequences from killing an innocent are future features.

### PG-007 - Travel between towns

**Promise and entry:** A player previews a legal route, departs, advances trail days, resolves available encounters and resources, completes the journey, and acknowledges arrival in the selected destination. Existing hostile trail encounters remain. Generated interactive friendly trail-NPC encounters are not part of 0.1.0.

**Authority, failure and history:** The server owns route progress, actions, resource outcomes and arrival. Remaining resources floor at zero; daily food upkeep consumes a meal when available, otherwise costs 25 HP. Any cause reaching zero health records terminal death in the same committed operation and stops later rewards/arrival. Pending choices, refresh and retry cannot charge a day or effect twice. The full [travel and resource contract](gameplay.md) owns exact outcomes.

**Dependencies:** **Requires** an active game, a legal route from `PG-003`, and resources/equipment as applicable from `PG-004`. Journey completion **changes** town/visit/context state used conditionally by `PG-004`, `PG-005` and `PG-006`. `PG-008` consumes the recorded account of journey events.

**Assessment and evidence:** Partial. Travel bounds resource losses, charges the 25-health toll once per unfed trail day, floors lethal health at zero, records terminal death, stops later journey effects and projects failed status to HUD/journal. Losing mounted travel recalculates remaining days from unchanged distance while preserving outstanding delays; arrival requires zero remaining distance and days. Terminal failure permits only map/journal reads until archival. Domain/replay and PostgreSQL/API coverage addresses these rules, remaining-distance resume and quiet-route completion/acknowledgement. The [travel replay tests](../tests/WildBunch.Domain.Tests/EventSourcing/TravelReplayEqualityTests.cs) compare completed journey records after independent replay. Same-tab client coverage addresses immediate HUD-clock and remaining-distance updates before refetch. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes departure and active-journey restoration, one-day progress, a deterministic hostile Fight with ammunition settlement and journal restoration, and a quiet completed trip whose acknowledgement/restored town do not duplicate commands. These are bounded local routes; other transitions, encounter failure/retry variants, cross-tab state, deployed behavior and whole-feature qualification remain unestablished. The [historical travel assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-domain-layer-investigation.md) and [persistence assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-persistence-layer-investigation.md) distinguish source review from runtime coverage.

**Terminal persistence coverage:** Local PostgreSQL API acceptance covers lethal starvation, fresh failed game/journal reads, the death entry, restricted actions, rejection of repeated advance without new events, and archive retaining the prior Failed status. This does not establish other death causes, a production-browser death route, hosted release behavior or complete travel qualification.

**0.1.0 disposition:** Retain and repair legal travel, hostile encounters, resource settlement, death and arrival. Generated interactive friendly trail-NPC encounters and their exclusive choices/weights/developer option are retired; friendly strangers are not converted into enemies and no replacement interaction is added. Hostile encounters remain a retained travel path, so PG-007 remains partial.

### PG-008 - Keep a casebook and journal

**Promise and entry:** The player can open the casebook to review accumulated clues, notes and public wanted information, including details about people marked as captured. Capture changes the person's status; it does not tear out or hide the page. The player draws conclusions. The player can also read one in-world journal: a full-playthrough view and a journey-focused view of the same authored history.

**Authority, failure and history:** Both views derive from the same authoritative event stream. Casebook records include only learned facts and explicit identity associations; unknowns stay unknown, and an unnamed observation does not become a named sighting from a feature match. Journal narration reports established player actions and effects without inventing provenance, success or technical audit text. Repeated reads do not create history. Developer audit is a separate audience projection, not another source of truth.

**Journal ownership:** `/journal` and `JournalLogProjector` supply the authored player history. Unique citizen-fine and rejected saloon outcomes are narrated; delegated wanted-person and settlement events retain separate ordered entries without an additional duplicate combined saloon summary. Journey views filter that same history. HUD notices, developer full audit and structured `TravelDiaryDay` state/cache remain separate projections.

**Dependencies:** **Consumes** established world/session facts from `PG-001`, knowledge from `PG-005`, outcomes from `PG-006` and `PG-007`, and the selected `PG-002` history. Opening either view does not require a completed investigation.

**Assessment and evidence:** Partial. Generated warrants have explicit stable suspect associations in CaseFileGenerated v3; historical v2 upcasts retain unknown identity without name-based inference. Application reads preserve learned clues/warrants through capture, attach settlements only to the associated warrant and omit internal IDs from player DTOs. Domain/replay/stale-snapshot coverage distinguishes living captures from dead settlements and rejects alias collisions against an explicit warrant target. Case-file component coverage retains the supplied case summary and same-name records while keeping that summary out of the journal overlay. Journey history filters the full journal by recorded sequence while retaining identical message/day/turn records and separate structured travel-day detail; persisted two-journey coverage addresses filtering after reload. [Local production-browser coverage](../src/WildBunch.Web/browser-tests/player-startup.spec.ts) includes opening the event-derived case lead before town selection without advancing the prologue, restoring learned evidence/captured status/paid settlement after take-in, and restoring the same hostile-encounter entry in Journal and Travel diary without another mutation. These checks do not establish every case-file state, other journal entries/journeys/browser engines, developer setup context transitions, deployment or the complete casebook lifecycle. The [current casebook/journal rules](gameplay.md) and [historical Web assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-web-layer-investigation.md) retain the product boundary.

**0.1.0 disposition:** Retain and repair an organized, truthful casebook and one event-derived journal with full and journey views. Retire automatic identity/deduction assistance as a separate future feature; keep full developer audit out of player surfaces.

**Authority and history:** The one-time `20261008180000_InvalidatePreAlphaPlaythroughs` migration deletes all existing `GameSessions` rows and dependent event/cache rows through existing foreign-key cascades when applied. It preserves schema and applied migration history; it does not drop or recreate a database or migration chain. This describes the migration contract, not a claim that any external database has already been migrated. See [PG-009-R](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-unrelated-criminal-removal.md). The distinct future addition is [PG-009-A](#pg-009-a---independent-bounty-targets-deferred).

**Dependencies:** The former shell shares generic warrant/poster, identity, wallet and settlement concepts with `PG-005`, `PG-006` and `PG-008`; those shared behaviors remain. The future feature would require lawful discovery, active encounter, identity, secured-person settlement and replay/persistence; the deferred PG-009-A entry below owns those details.

**Assessment and evidence:** The live unrelated roster, ledger, settlement event, replay/projection effects, codecs and feature-only tests have been removed. The [dependency assessment](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-unrelated-criminal-feature-boundary.md) records the pre-retirement source audit; the [Domain](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-domain-test-followup.md) and [Persistence](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-persistence-test-followup.md) test audits record the disposition of tests that protected that shell.

### PG-010 - Lawman pursuit and pressure

**Promise and entry:** No active lawman pursuit feature is promised in 0.1.0. The displayed heat value is not a promise of tracking, interception, route danger or encounter difficulty.

**Authority and dependencies:** The current ADR defines heat as town/lawman attention, not trail danger; it currently has no lawman effect. Future pursuit **requires** a separately designed lawman, recorded movement and lawful player-facing information. It is not a prerequisite for retained hostile trail combat in `PG-007`.

**Assessment and evidence:** Planned only for the pursuit lifecycle. Existing heat state/display does not constitute one. See [ADR-0029](decisions/ADR-0029-heat-is-future-lawman-pressure-not-trail-danger.md) and the [Domain investigation](https://github.com/HarleyBartles/wild-bunch/blob/6ab221b9d7616d6f549fa5e1a026acda82cf0fc3/.agents/investigations/stable-0.1.0/2026-10-07-domain-layer-investigation.md). No pursuit runtime or test proof is claimed.

**0.1.0 disposition:** Excluded; retain truthful heat meaning and record lawman pursuit as future work.

### PG-011 - Telegraph information

**Promise and entry:** The telegraph is present as a core town service but unavailable in 0.1.0. Sending a telegram and following a lead are distinct claims; action vocabulary or clue types alone do not establish a working player interaction.

**Future boundary and dependencies:** The first future telegraph capability is lawman intelligence: lawfully bribe a clerk to read a report of the lawman's recorded location, movement and timing, with source and age visible. It **requires** `PG-010`'s lawman and event-backed movement/report facts. A later iteration may add other telegraph clue types. A stale report must not become an omniscient current-position query.

**Assessment and evidence:** Disabled/unreachable. Current code has disabled navigation and dormant or misleading gang-clue/send vocabulary. ## Deferred capability requirements

These entries retain supplied future intent, not implementation authorization or a delivery sequence. Design them against the future repository before planning implementation; do not restore retired shells wholesale. Historical investigations linked above explain prior source, not current feature requirements.

### PG-009-A - Independent bounty targets (deferred)

**Story:** Discover a warrant for someone outside the Wild Bunch, encounter and identify that person, lawfully secure them under the warrant's terms, and receive the permitted sheriff bounty once. Saloons may contain citizens, gang members, unrelated wanted people or nobody. Gang members already have bounties; this addition concerns non-gang targets. Wanted status, gang membership, case involvement and murder guilt remain separate.

**Integration requirements:** Generate stable person/warrant identities and legal terms with recorded authoritative generation facts, without adding outsiders to the gang roster merely to reuse SuspectId. Record public discovery and identifying knowledge. Integrate eligible non-gang targets into normal deterministic saloon selection with coherent visits, exhaustion and active presence; developer setup arranges legal candidates, not final results. Resolve declarations against public handles and actual authoritative presence. Record the chosen surrender, flight, death or secured outcomes before settlement; accepting a warrant ID and an alive flag without capture is insufficient. Apply alive-only/dead-or-alive terms, exact costs and one payout through real application/API/player paths, rejecting unknown, inactive, unsecured, invalid-death and duplicate settlements. Same-name people remain distinct.

**Authority and dependencies:** Commands decide legality, events establish identity/availability/capture/settlement, and safe queries and journal report those facts without mutation. Save/resume and independent event replay preserve the full lifecycle and wallet. It **requires** supported generated target/warrant facts from PG-001 and **consumes** public discovery/identity from PG-005, encounter/declaration conventions from PG-006, history/display from PG-008 and persistence/resume from PG-002/PLAT-001. PG-004 supplies equipment and resource effects conditionally; purchasing is not a universal prerequisite. An unrelated settlement must not solve the central crime or advance gang release. Future migration and developer isolation follow the then-supported compatibility policy. Retirement PG-009-R is historical context, never a runtime ledger dependency. No generic NPC platform, broker or separate aggregate is implied.

**Open choices:** Encounter distribution, population size, replacement and exhaustion, interaction with gang progress, prior-discovery requirements, confrontation choices, transport to a sheriff versus immediate settlement, time cost, balance and content volume. The old three-times roster and parity rule are not requirements. If replacement is chosen, its availability transitions and exhausted states need event-backed behavior. Revalidate and re-author content; no removed roster is an approved future pool. A future design must prove a normal discover/identify/secure/settle path, independent reload/replay, truthful public reads and the genuine identity/legality/payment negatives.

### PG-004-A/B - Vendors, equipment and consumables (deferred)

Distinct stable/gunsmith services require meaningful town availability, reachable navigation, service-specific catalogs/prices, server validation of purchase town/service, inventory/horse/weapon integration and safe reads. Vendor-dependent economics belongs here. How prosperity affects each service and whether visiting or buying costs time remain open. Merely restoring a vendor enum on one store does not deliver this story. Future town-specific service availability must be recorded and reconstruct correctly, without changing the current common service set or inventing a configuration platform.

A Rifle addition must deliver acquisition, compatible stackable ammunition, one-per-type ownership, weapon-specific travel-combat effects, theft/resource handling, event-backed replay and truthful inventory/journal reads together. The original game's distinct Colt .44/.45 weapons and compatible ammo are future reference material, not currently supported goods. Snakebite medicine likewise requires an agreed acquisition and actual gameplay consumer; an item enum alone is insufficient. Neither authorizes expanding the current revolver baseline.

### PG-006-A/B/D - Saloon combat, recognition and resistance (deferred)

A named gunfight is a separate choice from take-in. Winning requires a gun and compatible ammunition; accepting without either remains reachable and kills the player, rather than being silently disabled. With both, victory still depends on the future combat rules. Victory and correct identification are independent: taking a misidentified innocent person's body to the sheriff results in arrest for murder. Consequences for other wrong declarations remain open. Killing the actual culprit loses the hunt immediately, regardless of prior player knowledge, while lawful corpse bounty collection remains possible afterward. Do not postpone loss until settlement or use a blanket terminal guard that forbids that specified payment. Record and replay death, failed hunt and the permitted one-time settlement distinctly. Capturing the culprit alive has a separate, still-unsettled clear-name/win contract. Combat probabilities, damage, time and exact terminal permissions need future design; existing hostile trail combat is a separate retained capability.

Sheriff recognition of a misnamed wanted person depends on that town's received poster and sheriff knowledge, not the globally generated warrant or player's poster list. Design circulation, recognition/nonrecognition, information timing, settlement/payment/roundup effects and recorded provenance before changing the current correct-name requirement.

Resistance may add escape and injury from attempted take-in. The bottle blow, blackout and five-HP-loss example illustrates intent, not a universal damage/probability rule. Decide outcome distribution, resource/time costs and persistent availability, then record actual outcomes without resampling on replay. A failed capture cannot pay bounty or advance roundup. Citizens' quiet cooperation and mistaken-take-in fine remain distinct. Current wanted-person gun ownership remains binary until that future design changes it.

### PG-007-A - Non-hostile trail people (deferred)

A friendly trail encounter needs its own player story, meaningful choices and event-backed outcomes before generation is reintroduced. Do not route a friendly stranger through Run/Fight/Bribe and default hostile resolution, classify them as an enemy or restore a message-only shell. Design its resource/time/history integration separately from the working hostile and environmental travel paths.

### PG-008-A - Casebook assistance (deferred)

Richer connections or deduction assistance needs an explicit player story distinguishing organization, player hypotheses and established facts, with ambiguity handling, public-only inputs and stable associations. Learned evidence must remain available after capture and same-name people must stay distinct. Do not infer identity from matching prose, promote a theory to world truth or restore removed mapper inference as a completed feature. No manual notes editor or pin-board UI is implied by the current paper-file metaphor.

### DEV-001-A - Town-layout preview (deferred)

A developer may later visit a town and preview alternative salts using its recorded world/town inputs and the normal rendering contract. Preview must leave the authoritative layout unchanged and normal visits must never regenerate it. Persisting a replacement needs a separate explicit state-transition design. A salt control must name an actual consumer and its lifecycle point; declared road-salt fields or speculative mystery remix are not delivered controls. Do not reroll settled world/layout/case facts, restore the retired prep/start path, build a generic control framework or invent new salted mechanics to justify a panel.

## Supporting platform requirements

### PLAT-001 - Event history, saved state and recovery

**Purpose and scope:** Event history is the only authority for what happened. The continuously maintained cache supplies current game state; when invalid, supported history rebuilds it. Snapshots and projections are caches, and read models never create gameplay facts. Preserve the event/schema migration chain and upcasters for retained facts. No pre-0.1.0 random playthrough needs retention; any initial discard is explicit and scoped to playthrough data/dependent events/caches, never a database reset or migration-history deletion.

**Assessment and dependency:** Partial and required by `PG-001`, `PG-002` and every feature that persists, resumes or projects an outcome. Normal genesis and recorded salts replay without sampling new randomness. Command and applicable player/journal reads recover stale or invalid caches from supported ordered events; envelope, components, events and diary rows are read from one PostgreSQL `RepeatableRead` snapshot. Recovery reads leave stored cache payloads, component versions, stream positions, event history and diary metadata unchanged. A later legal command repairs caches through the normal unit of work. Stale snapshot metadata must not apply already-current component effects twice.

**Supported component recovery:** Required current-version player wallet/inventory/items, world towns, CaseFile suspects, clock day/turn and pursuit heat recover when their required fields are null. Command loads also validate SaltSource salt/mode; player and journal queries do not consume that component. Missing setup, null entropy and unsupported entropy enum values recover event-recorded setup through command and player reads; the legacy whole-session snapshot retains its separate Classic default. Journey recovery covers missing active journeys and malformed route profiles when ordered start/travel/acknowledgement facts establish the state; an acknowledged journey remains absent until a new start. Town visits recover event-recorded visit/person/saloon-source state, including rejection of a wanted person without a suspect ID; a genuine citizen and setup-only absence remain valid. Command loads recover current action context, event-established wanted-person presence and completed journey history. An absent empty presence ledger stays valid without a state-changing confrontation; test-only presence seeded without events has no recovery promise. Completed history is compared with ordered acknowledgement facts, while no-acknowledgement absence remains empty. Typed snapshot restoration retains action context, clock, stream version and structured travel terrain, route water and canteen charges.

**CaseFile recovery:** Current caches are checked against generated facts and applicable later events. This includes culprit and ordered suspect facts, opening lead, release threshold, turf assignments, event-established accusation/release progress, and discovered-suspect membership from genesis plus revealed public clues. Discovery order is non-semantic. Missing/null required discovery lists, opening leads and public clue pools recover only from valid recorded facts. Known/public clue pools preserve complete ordered payloads and nested anchors; known/public warrants preserve complete ordered payloads, terms and nullable stable target identity. A historical null target stays unknown when that is what history records. Legitimate empty pools remain valid, and unlearned clues, warrants and culprit truth remain private in player/journal projections. Ordered sheriff settlements and non-Abandoned confrontation states are checked against their event-recorded payloads and action clock. Recovery preserves captured-person status, known evidence and wallet effects, rejects duplicate payout and repairs on an ordinary save without inventing investigation or confrontation events. Raw duplicate records discarded by Domain normalization are outside the confrontation-cache contract.

**Diary recovery:** The cache records its applied stream version and projected day count. Missing trailing/interior rows, orphan rows, null legacy watermarks and stale/mixed-version rows rebuild the whole supported projection from events. Current-version rows retain their stored content. Reads do not write back; the next legal command save repairs sequence-keyed rows in its existing unit of work. Structured `TravelDiaryDay` state remains distinct from the authored player journal described in `PG-008`.

**Evidence and limits:** [PostgreSQL repository behavior tests](../tests/WildBunch.Integration.Tests/EfGameSessionRepositoryTests.cs) exercise supported component corruption, stale tails, read preservation, ordinary-save repair and fresh loads through production command/player/journal paths. [Payload-version tests](../tests/WildBunch.Integration.Tests/Versioning/VersionMismatchBehaviorTests.cs) cover the payload-loader boundary; they do not independently establish PostgreSQL recovery. Supported `WorldGenerated` v1 history without an embedded CaseFile can recover via a following valid `CaseFileGenerated`; its original event payload/schema is preserved through reads and save. Missing required generation facts, undecodable authoritative events and unsupported history fail closed. These are bounded recovery and compatibility contracts, not exhaustive nested-cache corruption coverage or general historical event/component/projection/migration compatibility. The no-generation-event compatibility boundary remains scoped to existing supported behavior. Event/schema versions, upcasters and migration history remain authoritative under [ADR-0028](decisions/ADR-0028-onion-ddd-cqrs-event-sourcing-and-projections-posture.md). Town-specific warrant circulation is separately deferred in `PG-006-B`.

**Disposition:** Required supporting capability for stable 0.1.0; not a player feature by itself. Remaining compatibility and recovery limits do not imply hosted accounts, public deployment or exhaustive release qualification.

### PLAT-002 - Public identity and session isolation

**Purpose and scope:** A future public browser deployment needs a player identity associated with saved playthroughs, Google sign-in as the selected starting provider, and server-side ownership checks so one player cannot read or act on another player's game. The pre-alpha local baseline has no public login or multi-user isolation and cannot be exposed as the public game until those boundaries exist.

**Assessment and dependency:** Not implemented in the 0.1.0 local release. This is a prerequisite for public deployment and account-backed resume in `PG-002`; browser session expiry must not become game-state authority.

**Disposition:** Excluded from the local 0.1.0 baseline; owned by the separate [cloud playability specification](../.agents/specs/2026-10-06-cloud-playability-and-releases.md).

### PLAT-003 - Environment isolation and cloud delivery

**Purpose and scope:** A future cloud release requires containerized application delivery, infrastructure-as-code or an equivalent reproducible deployment definition, separate developer/preprod and public-production access, and a deliberate release path. Kubernetes is not currently justified. The purchased OVH VPS is the selected initial host, using separate Docker Compose deployments; capacity and operational readiness still need verification.

**Assessment and dependency:** Not implemented by this local baseline. It depends on user isolation in `PLAT-002`, and preprod must not expose developer controls to public play. The developer playtest environment is a preproduction environment, not a second public audience.

**Disposition:** Excluded from the local 0.1.0 baseline; the [cloud roadmap](../.agents/roadmaps/2026-10-06-cloud-playability.md) owns the later deployment investigation.

### PLAT-004 - Versioned integration and release identity

**Purpose and scope:** Gitflow uses `develop` for ordinary integration PRs and `main` for qualified releases/hotfixes. One authored application version lives in `Directory.Build.props`; every merge to `develop` advances one `0.1.0-dev.N` checkpoint, and release candidates/stable releases bind to verified source and derived artifacts.

**Assessment and dependency:** Delivered for the local baseline, with hosted release and deployment flows still unqualified. The pinned Gitflow/SemVer policy governs generated `dev.N`, `rc.N` and stable identities. `release-verify --check` builds API, public-web, and playtest-web outputs from one clean source commit and binds their file-tree SHA-256 digests to that commit and the authored version in an ignored immutable local bundle. Re-running verifies existing bytes without rebuilding or overwrite. The command bus builds and validates production web artifact identity before Chromium tests; the retained local startup/town browser route uses the real API and PostgreSQL. This identifies the produced bytes and qualifies one local route; it does not claim separate builds are reproducible, complete candidate qualification, hosted release behavior or public deployment. This release-support capability supports delivery of every included feature but does not change player gameplay. Pre-1.0 development makes no public API or gameplay-compatibility promise; this product's current `0.y.z` policy is recorded in the [release specification](../.agents/specs/2026-10-06-cloud-playability-and-releases.md).

**Disposition:** Required release support. Every changed release candidate needs its own source-bound qualification. [ADR-0048](decisions/ADR-0048-gitflow-and-semver-release-lifecycle.md) and the [release runbook](../.agents/runbooks/release.md) own the reusable release rules. Future `1.0.0` compatibility remains undecided.

## Cross-cutting boundaries

CQRS and event sourcing apply at the implementation boundary: commands validate and produce facts through the game aggregate; queries return safe projections; replay restores recorded facts without rerolling randomness. These are system obligations, not dependency edges between every pair of features. The [backend architecture unslop profile](../.agents/unslop/backend-architecture.md), [architecture guardrails](../.agents/doctrine/architecture-guardrails.md) and [event-sourcing integrity doctrine](../.agents/doctrine/event-sourcing-integrity.md) own their implementation constraints.

The game can be a stable, intentionally incomplete `0.1.0`. An unfinished hunt, deferred lawman, disabled telegraph, removed unrelated-criminal loop, or future developer tool does not become a hidden promise because the code contains a matching enum, type or test. Update this matrix when those promises or their dependencies change, and keep future additions separate from the retirement work that clears the 0.1.0 boundary. Container delivery, infrastructure-as-code and environment isolation remain in the separate [cloud roadmap](../.agents/roadmaps/2026-10-06-cloud-playability.md).
