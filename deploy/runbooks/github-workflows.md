# GitHub deployment workflows

The infrastructure, database-initialization and release workflows run only by manual dispatch from `main`. Pull requests, forks and ordinary pushes cannot request AWS credentials or the CodeBuild runner. The game has no public endpoint; the EKS administration endpoint remains restricted to the engineer's `/32` and IAM authentication.

Before enabling these paths, complete the local bootstrap from [the AWS bootstrap runbook](aws-bootstrap.md), apply the reviewed environment plan through the infrastructure workflow, authorize the GitHub App connection in AWS, and configure the GitHub environment `wild-bunch-learning` to allow `main` only and require a human reviewer for apply, destroy, database initialization and release jobs. Verify the deployed CodeBuild webhook matches the exact release workflow name, `WORKFLOW_JOB_QUEUED` and `refs/heads/main` filters before using the private runner.

Configure these GitHub environment secrets after bootstrap: `WB_TF_STATE_BUCKET`, `WB_INFRASTRUCTURE_ROLE_ARN`, `WB_IMAGE_PUBLISHER_ROLE_ARN`, `WB_DATABASE_INIT_INVOKER_ROLE_ARN`, `WB_ENGINEER_IAM_ROLE_ARN` and `WB_ENGINEER_IPV4_CIDR`. After an authorized environment apply, save the non-secret Terraform `environment_contract` output as the protected GitHub environment secret `WB_ENVIRONMENT_CONTRACT_JSON`; it includes resource identifiers and the private database endpoint, but no database credential values. AWS runtime, migration and administrator credentials remain in Secrets Manager.

The infrastructure workflow has four modes. `plan` and `destroy-plan` require a full source commit SHA reachable from `main`, save the exact Terraform plan and full diagnostics under the encrypted, versioned private S3 `plans/<plan-id>/` key, and print only source identity and aggregate action counts to GitHub. A plan ID contains the source SHA and workflow run/attempt identifiers. Review the exact plan from an access-restricted machine before dispatching `apply` or `destroy` with that plan ID; those jobs pass through the protected environment again and apply the saved plan against the same Terraform source revision and backend state. Terraform's S3 lockfile also serializes state changes. Plan objects and noncurrent versions expire after seven days.

To inspect a saved plan, use the `wild-bunch` AWS profile with private access to the bootstrap bucket, check out the source SHA embedded at the start of the plan ID, initialize the environment root against the same backend, download `plans/<plan-id>/terraform.tfplan` to a private temporary directory, and run `terraform show` locally. The full workflow logs are also stored privately beside the plan. Do not upload either file to GitHub artifacts, logs, pull requests or this public repository.

Run `Wild Bunch Learning Database Initialization` after verifying the RDS endpoint and before the first application release. It accepts only a full commit SHA reachable from `main`, starts the separate private initializer CodeBuild project with that exact source version, and polls its build. The GitHub role can start and inspect the project but cannot read the RDS administrator or application secrets; the CodeBuild service role retrieves the administrator credential inside the VPC. If monitoring times out, inspect the existing build before retrying.

Run `Wild Bunch Learning Release` in `deploy` mode with a trusted source SHA and a human-authored compatibility acknowledgement covering schema, constraints, stored data/events and writes against the current and recovery application versions. End the acknowledgement with `recovery: selected-known-good` when a release is already recorded, otherwise use `recovery: none`; the hosted publisher resolves the actual prior release ID privately and validates the acknowledgement before transfer. The pipeline runs canonical CI and deployment tests, builds or reuses immutable SHA-tagged ECR images, resolves their digests, and writes only a non-secret release contract to private S3. It never writes that contract, the environment contract or the Terraform plan to GitHub artifacts or job output.

The private CodeBuild runner receives only the validated SHA and release ID after the hosted publisher succeeds. Its AWS service role supplies ECR, private S3, Secrets Manager and namespace-scoped Kubernetes permissions; GitHub does not pass static AWS credentials. The release controller runs one retained migration Job, checks schema history, deploys the digest-pinned frontend/API, verifies readiness, actual image identity and HTTP behavior, then advances the known-good pointer. A failed release does not automatically undo migrations or select the new version. Use `recover` mode with the exact earlier known-good release ID after diagnosing the failure; recovery restores the recorded workload and credential references and leaves database history intact.

Workflow success proves only the operations that actually completed. It does not make the pre-alpha game suitable for unauthenticated public players, establish production operational experience, or replace authorized AWS cleanup. Follow [the teardown runbook](teardown.md) before ending the temporary environment.
